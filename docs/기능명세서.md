# 1부 — 앱 기능 명세

## 1. 제품 개요

밤에 갈 클럽을 **지도 · 조건 · 장르**로 찾는 앱.

핵심 가치 3가지:
1. **지금 갈 수 있는 곳** — 영업 중 / 지금 이 시간 무료입장 / 오늘 공연
2. **조건으로 고르기** — 입장비 무료 · 서비스 음료 · 금연 · 장르(힙합/EDM/K-POP)
3. **가기 전에 확인** — 테이블 배치도·가격, 메뉴판, 사진, 리뷰, 편의시설

### 1.1 베타 범위

| 포함 | 제외 |
|------|------|
| 회원가입·로그인(카카오·네이버·본인인증) | 웨이팅 · 테이블 예약 |
| 홈 / 검색 / 내 주변 / 찜 / 마이페이지 | 분실물 찾기 |
| 클럽 상세(정보·메뉴·사진·리뷰·매장정보) | 결제 내역 |
| 인앱 리뷰 작성·수정·삭제 | 블로그 리뷰 |
| 고객센터 문의 | Apple 로그인 (버튼만 존재) |
| 회원 탈퇴(30일 보관) | 푸시 알림 (FCM 인프라 없음) |

## 3. 앱 진입 흐름

```
main()
 └ dotenv.load → Firebase.initializeApp → KakaoSdk.init → FlutterNaverMap().init
 └ ProviderScope(observers: [NetworkFailureObserver])
    └ SplashGate → NetworkGate → VersionGate → AuthGate → MainScaffold
```

| 게이트 | 판정 | 실패 시 | 위치 |
|--------|------|---------|------|
| **SplashGate** | 인트로(min 2.6s / max 5.5s) + GPS 1회 조회. 다음 목적지가 정해질 때까지 아래 게이트를 만들지 않는다 | — | `presentation/common/splash_gate.dart` |
| **NetworkGate** | ① `InternetAddress.lookup('firestore.googleapis.com')` 실제 도달 ② 답이 없을 때만 `connectivity_plus` 연결 종류 | 연결 안내 화면 | `presentation/common/network_gate/` |
| **VersionGate** | 점검 → 강제 → 권유 → 통과 | 전체화면 차단 / 1회 바텀시트 | `presentation/common/version_gate/` |
| **AuthGate** | `decideSessionAction()` — uid + `isVerified` + 토큰 유효성 | Welcome 화면 | `presentation/auth/auth_gate.dart` |

- 전부 **fail-open** — 조회 실패·타임아웃·문서 없음은 통과. 게이트는 차단 장치가 아니라 **안내 장치**
- 재검사는 `AppLifecycleState.resumed`(앱 복귀)에만. 사용 중 화면만 옮기는 동안엔 재검사하지 않는다
- `NetworkFailureObserver`가 ProviderScope에 붙어 **어떤 요청이든 실패하면 연결을 다시 확인**한다
- 세로 방향 고정(`portraitUp`) · 네이버맵 마커 임시파일 삭제 예외(`FileSystemException`)는 `PlatformDispatcher.onError`에서 삼킨다

|----|------|------|------|
| AU-01 | 카카오 로그인 | SDK accessToken → `kakaoLogin` → Custom Token. uid `kakao:{id}` | ✅ |
| AU-02 | 네이버 로그인 | SDK accessToken → `naverLogin` → Custom Token. uid `naver:{id}` | ✅ |
| AU-03 | 본인인증 시작 | '본인인증으로 시작하기' 바텀시트 → 이름·생년월일·번호·통신사. uid `phone:{phone}` | 🟡 문자 인증 코드 `'123456'` 하드코딩 |

| AU-07 | 프로필 입력 | 이름·성별·생년월일·전화번호. 성별은 주민번호 뒷자리 첫 숫자에서 도출(`genderFromCode()`) | ✅ |
| AU-08 | 닉네임 자동 배정 | 가입 마지막에 `updateUserProfile`을 **인자 없이** 호출 → `{앞말}바이버{1000~9999}` (조합 36만) | ✅ |
| AU-09 | 가입 완료 화면 | 재로그인 경로는 건너뛰고 홈 직행(`enterHomeAfterAuth()`) | ✅ |
| AU-10 | 자동 로그인 | Firebase Auth 네이티브 세션 + `LocalPrefs.autoLogin`(기본 켜짐) | ✅ |
| AU-11 | 로그아웃 | Firebase + **카카오·네이버 SDK 세션까지** 정리(`social_auth_datasource`, 각 3초 타임아웃) | ✅ |
| AU-12 | 죽은 계정 감지 | `refreshSession()` = `getIdToken(true)`. 무효 코드 5종만 false | ✅ |
| AU-13 | 가입 중단 정리 | `abortSignup()` — pending token 폐기 + 로그아웃. 이름·번호 빈 유령 계정 차단 | ✅ |
| AU-14 | 탈퇴 대기 복구 안내 | 복구되면 `kAccountRestoredMessage` 토스트, 본인인증 경로는 `kAccountRestoreNotice`로 예고 | 🟡 서버 미배포 |
| AU-15 | 약관 전문 화면 | Welcome·설정 양쪽에서 같은 `TermsDetailScreen` | ✅ |

**앱 쪽 흐름**

```
Welcome → SignupMethod 결정 (카카오·네이버 버튼 / '본인인증으로 시작하기')
 → IdentityVerificationScreen(method:)
 → '확인' 에서 주인 판정 먼저 (약관 시트보다 앞)
    · 차단 → 토스트 + abortSignup()
    · 내 계정 → 약관 생략 → CertificationNumberScreen(isLogin: true)
    · 신규   → 약관 시트 → CertificationNumberScreen(isLogin: false, agreements:)
 → 인증번호 화면에서 한 번 더 판정 → phoneLogin/finalizeLogin → saveUserProfile
 → updateUserProfile()(인자 없음 = 랜덤 닉네임 배정) → 가입완료 → 홈
```

- `SignupMethod`를 화면까지 들고 다닌다 — 같은 화면에 소셜·본인인증 두 경로가 들어오고, 세션 유무로 추측하면 '카카오 시도 후 되돌아와 본인인증' 순서에서 틀린다
- 주인 판정을 약관 시트보다 앞에 둔다 — 판정 전에는 가입인지 로그인인지 알 수 없다
- 인증번호 화면에서 **재판정** — 앞 화면 통과와 계정 생성 사이에 다른 기기에서 같은 번호가 가입될 수 있다
- 재로그인은 `saveUserProfile`을 부르지 않는다 — `updatedAt`이 갱신돼 수정한 적 없는 계정이 로그인마다 수정된 것으로 남는다

| 미표시 조건 | 이유 |
|-------------|------|
| `type == 'none'` | 무료 없음 |
| `type == 'always'` | 상시 무료 — 나눌 시간대가 없어 도형이 한 칸. '무료'는 입장료 행이 이미 알린다 |
| timed인데 쓸 수 있는 창이 없음 | 그릴 게 없다 |
| 다음 무료 시작이 `leadTime`(1시간)보다 멀다 | 무료가 여섯 시간 뒤인데 카운트다운이 홈 탭 첫 자리를 종일 차지하면 안 된다 |

- 무료가 **진행 중**이면 남은 시간이 곧 알맹이라 무조건 표시
- 표시 판정은 **화면을 만드는 시점 한 번** — 이미 떠 있는 섹션은 무료가 끝나도 그대로 두고 헤드만 '다음 무료입장'으로 바꾼다(스크롤 튐·정보 소실 방지). 다시 숨기는 건 다음 진입 때
- 영업 여부는 판정과 **같은 시각**으로 묻는다 — `OperatingHours.dayAt(now).isOpenAt(now)`. `today.isCurrentlyOpen`은 벽시계를 읽어 섞으면 "무료 창 안인데 영업 종료"가 나온다

> ⚠ `NestedScrollView.headerSliverBuilder`에 pinned `SliverPersistentHeader` 금지 — Flutter 3.41 세만틱스 검증이 매 프레임 `'!semantics.parentDataDirty'` assert를 던져 화면이 통째로 안 그려진다. sticky 바는 스크롤 밖 고정 행으로 구현.

### 5.1 ⚠ 라운드 카드 테두리

클립되는 카드의 테두리는 `decoration`이 아니라 **`foregroundDecoration`**에 둔다.

```dart
Container(
  clipBehavior: Clip.antiAlias,
  decoration: BoxDecoration(gradient: ..., borderRadius: r),       // 채움만
  foregroundDecoration: BoxDecoration(border: ..., borderRadius: r), // 테두리는 자식 위
  child: ...,
)
```

`decoration`에 `border`를 넣으면 **직선부만 남고 코너 호에서 선이 사라진다**. Flutter가 `Container`를 `DecoratedBox > ClipPath(바깥 라운드렉트) > Padding(테두리 두께) > child`로 짜기 때문 — `decoration.padding`의 균일한 1px 인셋이 **코너 곡선을 따라가지 않아** 호 구간에서 자식이 선을 덮는다.
실측: 직선부 밝기 83 대 호 14~25, `foregroundDecoration`은 호 76~83. 바깥 `ClipRRect`로 감싸도 결과는 같다.

적용된 곳 14곳 · **아직 안 고친 곳 4곳**(`BackdropFilter`가 낀 라운드 표면): `vybe_toast` · `vybe_confirm_dialog` · `notification_header`(원형 버튼) · `search_bar`.

## 7. 인증 아키텍처

### 7.1 로그인 방식별 UID

| 방식 | 처리 | Firebase UID | 시점 |
|------|------|--------------|------|
| 카카오 | `kakaoLogin` → Custom Token | `kakao:{kakaoId}` | 베타 |
| 네이버 | `naverLogin` → Custom Token | `naver:{naverId}` | 베타 |
| 본인인증 | `phoneLogin` → Custom Token | `phone:{phone}` | 베타 |
| Apple | Firebase Auth 직접 | 자동 생성 | 이후 |

`accessToken`은 매번 달라지지만 소셜 ID는 불변 → **항상 같은 Firebase UID**가 나온다.
본인인증은 로그인 방식이 아니라 **신원 확인 수단**이다.

### 7.2 전화번호 주인 판정 (`checkPhoneDuplicate`)

차단 기준을 "번호 존재"가 아니라 **"주인이 누구냐"**로 바꿨다. 번호가 쓰인다는 사실만으로 막으면 본인인증으로 가입한 사용자가 로그아웃한 뒤 영영 못 들어온다(실제로 그랬다).

| 상황 | 결과 |
|------|------|
| 처음 보는 번호 | 약관 동의 → 문자 인증 → **가입** |
| 가입할 때와 **같은 방식**의 내 계정 | 약관 생략 → 문자 인증 → **로그인** (홈 직행 · Firestore 쓰기 0) |
| **다른 방식**으로 가입된 번호 | 차단 — `이미 존재하는 계정입니다.` + 계정 생성 안 함 |
| 탈퇴 대기(30일) — **본인 + 파기 전** | 통과 → 로그인하는 순간 **계정 복구** |
| 탈퇴 대기 — 남 / 파기일 지남 | 차단 (재가입 가능일 안내) |

**시도 중인 uid는 클라가 정하지 않는다** — 서버가 만든다.

| 조건 | 시도 중인 uid | 근거 |
|------|---------------|------|
| 이미 로그인된 세션이 있다 | `context.auth.uid` | 서버가 토큰으로 검증한 값 — 위조 불가 |
| 세션 없음 + `method === 'identity'` | `phone:{phone}` | 본인인증 uid는 번호 하나로 결정된다 |
| 세션 없음 + 소셜 신규 | 없음 | 로그인 전이라 users 문서가 존재할 수 없다 → 주인은 무조건 남 |

> ⚠ **주인의 uid·provider는 응답에 싣지 않는다** — 이 함수는 비로그인 상태에서 호출된다. uid를 내려보내면 번호만 넣어 보고 남의 `kakao:{id}`·`naver:{id}`를 캐낼 수 있다. 차단 문구에 "카카오로 가입된 계정입니다"처럼 가입 방식을 적지 않는 것도 같은 이유 — **계정 열거(enumeration)**를 돕게 된다. 비교는 서버에서 끝내고 `sameAccount` 불리언 하나만 준다.

**재로그인도 문자 인증은 그대로 거친다** — 번호 소유 확인 없이 통과시키면 남의 번호를 적기만 해도 로그인이 된다. 가입과 로그인이 갈리는 건 인증에 성공한 다음뿐이다.

### 7.3 세션 판정 (`decideSessionAction()`)

Firebase Auth는 네이티브에서 세션을 디스크에 저장하므로 **자동 로그인은 이미 동작한다**. 새로 만들 기능이 아니라, 자동 로그인이 상시 켜진 상태에서만 드러나는 **구멍을 막는 것**이 작업 범위였다.

**막아야 했던 구멍 4가지**

| # | 구멍 | 원인 |
|---|------|------|
| 1 | **유령 세션** — 로그인은 됐는데 프로필 미완성 | `finalizeLogin()`(세션 성립) → `saveUserProfile()` 사이에서 앱 종료·네트워크 실패. `onUserCreated`가 uid·provider만으로 문서를 먼저 만들어 **문서 존재 여부로는 판별 불가** → 판정 기준은 `isVerified` |
| 2 | **`isNewUser` 오판** | 로그인 함수가 돌려주는 `isNewUser`는 Auth user 존재 여부일 뿐 프로필 완성과 무관. 미완성 유저가 재로그인하면 `false` → 그대로 홈으로 간다 |
| 3 | **죽은 계정** | 다른 기기에서 탈퇴하거나 Auth가 비활성화돼도 로컬 세션은 살아 있다. 자동 로그인이라 재로그인 시점이 없어 영영 감지되지 않는다 |
| 4 | **소셜 SDK 세션 잔존** | `signOut()`이 Firebase 세션만 정리 → 카카오·네이버 SDK 세션이 남아 계정 전환 불가 |

**판정 결과 3가지**

| SessionAction | 조건 | 결과 |
|---------------|------|------|
| `none` | uid 없음 | WelcomeScreen |
| `keep` | uid 있음 + `isVerified == true` (또는 users 조회 실패 — fail-open) | MainScaffold |
| `signOut` | 자동 로그인 OFF · 또는 `isVerified == false`·문서 없음(유령 세션) · 또는 토큰 갱신이 서버에서 거부됨 | 세션 정리 → WelcomeScreen |

| 결정 | 이유 |
|------|------|
| 검사 끝나기 전엔 스플래시 유지 | 검사 중 Welcome을 잠깐 그리면 멀쩡히 로그인된 사용자에게 로그인 화면이 **번쩍인다** |
| 콜드 스타트 1회 + 복귀 시 토큰만 | 실행 중에 프로필 완성 여부를 다시 판정하면, 본인인증(외부 앱·웹뷰)을 다녀오거나 저장 직전인 사용자를 로그아웃시킨다 |
| 미완성 세션은 가입 재개가 아니라 **signOut** | 세션을 살린 채 본인인증 화면으로 직행시키면 뒤로가기·중도 이탈 경로를 전부 따로 처리해야 한다. Welcome부터 다시 태우는 쪽이 단순하고 안전하다 |
| `users.isVerified`가 **세션 유효성의 단일 기준**으로 승격 | 이 필드를 false로 되돌리면 다음 실행에서 자동 로그아웃된다. 값을 true로 올리는 곳은 `verifyIdentity`·`setUserProfile` 둘뿐 — **마이그레이션·어드민에서 일괄 수정 금지** |

**가입 이어하기 uid 보호** — 이미 세션이 있으면 `phoneLogin()`을 건너뛴다. 안 그러면 소셜 계정으로 로그인한 사용자에게 `phone:{phone}` uid가 새로 생겨 원래 계정이 프로필 없이 버려진다.

### 7.4 ⚠ 출시 차단 — 문자 인증이 아직 가짜다

- 인증번호가 `certification_number_handler.dart`에 **`'123456'` 하드코딩**
- `phoneLogin`은 번호만 받으면 아무 검증 없이 Custom Token을 발급한다
- 지금까지는 "이미 있는 번호는 차단"이 우연히 계정 탈취를 막고 있었는데, **재로그인을 허용하면서 그 방벽이 사라졌다**
- 즉 **남의 전화번호 + `123456`만으로 그 계정에 로그인된다**

**Firebase Phone Auth(실제 SMS) 연동 전까지 프로덕션 배포 금지.**

## 8. 앱 시작 게이트 체인 — 순서가 설계다

```
runApp
 ├─▶ SplashGate    # 연출(min 2.6s / max 5.5s) + GPS 1회
 ├─▶ NetworkGate   # 연결 없음 → 안내 화면 (fail-open)
 ├─▶ VersionGate   # 점검 / 강제 업데이트 / 권유 (fail-open)
 └─▶ AuthGate      # 세션 판정 → MainScaffold 또는 WelcomeScreen
```

| 순서 | 왜 이 자리인가 |
|------|----------------|
| NetworkGate가 VersionGate 위 | 연결이 없으면 버전 조회·세션 복원은 타임아웃만 먹고 빈 화면이 된다. **원인을 먼저 알려야 한다** |
| VersionGate가 AuthGate 위 | 강제 업데이트·점검은 로그인 전에 걸려야 한다. 그래서 `appConfig` Rules에 **auth 조건을 걸지 않는다** — 걸면 비로그인 유저가 안내를 영영 못 받는다 |
| 네트워크 확인이 스플래시 중에 시작 | `splashDestinationProvider`가 `networkStatusProvider`를 보므로 연출과 병렬로 돈다 — 대기 시간이 겹쳐 사라진다 |
| 팝업 광고는 체인 **아래** | 점검·강제 업데이트 차단 화면 위에 광고가 뜨면 안 된다 |

### 8.1 앱 실행 1회당 Firestore read

| 게이트 | 대상 | read | 타임아웃 |
|--------|------|------|----------|
| NetworkGate | Firestore 접근 없음 (connectivity + DNS lookup) | **0** | DNS 타임아웃 → 통과 |
| VersionGate | `appConfig/{platform}` | 1 | 3초 → 통과 |
| AuthGate | `users/{uid}` (비로그인이면 0) | 1 | 3초 → 통과 |
| 홈 진입 | `popupAds where isActive==true` | 1 | 실패 → fail-silent(안 띄움) |

세 게이트 전부 **fail-open**. 재검사는 `AppLifecycleState.resumed`에만.

### 8.2 네트워크 판정 2단계 (`device_network_datasource.dart`)

| 우선순위 | 확인 | 잡아내는 상황 |
|----------|------|----------------|
| ① | `InternetAddress.lookup('firestore.googleapis.com')` **실제 도달** | 성공=연결됨 / `SocketException`=연결 없음 |
| ② | 도달이 답을 못 냈을 때만 `connectivity_plus` 연결 종류 | 종류가 하나도 없으면 연결 없음, 그 외엔 통과 |

- ⚠ **연결 종류를 먼저 보고 끊지 않는다** — 와이파이가 막 붙었거나 기기가 상태를 늦게 갱신하면 종류와 실제 통신이 어긋나, 연결이 돌아왔는데도 안내 화면에 갇힌다
- ⚠ **도달 확인은 재연결 경로에서 여러 번**(`kReconnectAttempts` 3회 · 0.5초 간격) — 붙은 직후엔 인터페이스만 올라오고 DNS는 아직 못 쓰는 구간이 있어, 한 번 실패로 오프라인을 확정하면 **다시 시도 버튼을 눌러도 계속 실패**한다. 첫 진입만 1회(스플래시를 붙잡지 않으려고)
- iOS는 와이파이 설정 직접 진입이 OS 차원에서 막혀 '설정 열기'가 **앱 설정**으로 열린다(`app_settings` 폴백). Android는 와이파이 설정으로 직행

## 9. 기능별 백엔드 설계

### 9.1 약관 동의 기록

가입 시 어떤 항목에 동의/비동의 했는지를 유저별로 남긴다. 지금까지는 "필수 4개를 다 체크했다"는 사실만 화면에서 확인하고 **버리고** 있었다 — 어느 판본에 언제 동의했는지 증명할 수단이 없었다.

| 키 | 항목 | 필수 | 문서 |
|----|------|------|------|
| `terms` | 서비스 이용약관 동의 | 필수 | `LegalDoc.terms` |
| `privacy` | 개인정보 수집·이용 동의 | 필수 | `LegalDoc.privacy` |
| `location` | 위치기반서비스 이용 동의 | 필수 | `LegalDoc.location` — **위치정보법 §18**이 이용약관과 별도 동의를 요구 |
| `age19` | 만 19세 이상입니다 | 필수 | 없음 (확인 항목 — `version` 빈 문자열) |
| `marketing` | 마케팅 정보 수신 동의 | 선택 | `LegalDoc.marketing` |

```
users/{uid}.agreements = {
  terms:     { agreed: true,  version: "2026-08-20", agreedAt: <ts> },
  privacy:   { agreed: true,  version: "2026-08-20", agreedAt: <ts> },
  location:  { agreed: true,  version: "2026-08-20", agreedAt: <ts> },
  marketing: { agreed: false, version: "2026-08-20", agreedAt: <ts> },  // 안 눌러도 false 로 기록
  age19:     { agreed: true,  version: "",           agreedAt: <ts> }
}
```

| 결정 | 이유 |
|------|------|
| 서브컬렉션이 아니라 users 문서 안의 map | 항목이 5개 고정이고 프로필과 항상 같이 읽힌다. 가입 때 쓰던 `set(merge)` 한 번에 얹으므로 **read·write 추가 0** |
| 비동의도 `agreed: false`로 기록 | 키를 빼면 '거부했다'와 '아직 안 물어봤다'가 구분되지 않는다. 약관이 늘었을 때 누구에게 추가 동의를 받을지가 이 차이로 갈린다 |
| `version`(문서 개정일)을 같이 쓴다 | 개정하면 재동의 대상을 골라야 한다. 동의 여부만 남기면 구판·신판 동의자가 섞인다 |
| 키 = `LegalDoc.name` | 한글 라벨을 키로 쓰면 문구를 다듬을 때마다 전 유저 문서가 어긋난다 |
| 재로그인 경로는 안 쓴다 | `isLogin=true`는 약관 시트를 건너뛰어 `agreements`가 null로 내려온다 → 기존 기록을 덮지 않는다 |

- `agreedAt`은 **중첩 map 안의 `serverTimestamp()`** — Firestore는 sentinel을 중첩 map 안에서는 허용하지만 **배열 안에서는 거부한다**. 항목을 list로 바꾸면 쓰기가 통째로 실패한다
- `UserModel.toFirestore()`에서 `agreements`를 **일부러 뺐다** — 프로필 저장마다 map을 다시 쓰면 '동의한 시각'이 프로필 수정 시각으로 덮인다
- **이력은 안 남는다**(덮어쓰기). 철회 이력까지 필요하면 `users/{uid}/agreementLogs`를 따로 둘 것
- 기존 유저는 필드 없음 = 빈 map. **백필 안 한다** — 동의한 판본·시각을 모르는데 지어내면 그게 더 나쁜 기록이다

**백엔드 영향**: Rules 변경 없음(`agreements`는 금지 키가 **아니다** — 본인의 동의 여부라 마케팅 철회를 붙이려면 고칠 수 있어야 한다) · 인덱스 불필요(map, 쿼리 대상 아님) · Functions 불필요(집계 아님).

### 9.2 회원 탈퇴 — 30일 보관 soft delete

**요구가 두 축이라 "삭제"와 "숨김"을 나눴다.**

| 요구 | 뜻 |
|------|-----|
| ① 30일 보관 | 탈퇴해도 문서를 지우지 않는다. 30일 뒤 스케줄 함수가 파기 |
| ② 즉시 비노출 | 보관과 별개로, 탈퇴 즉시 리뷰·사진이 어디에도 안 보여야 한다 |

둘을 한 동작으로 묶으면 어느 쪽도 만족시킬 수 없다 → 문서는 남기되 **노출 경로에서만 빼고**(`isHidden`), 30일 뒤 스케줄이 실제로 지운다. **탈퇴 ≠ 즉시 하드 삭제.**

```
탈퇴 요청
 ├─▶ 즉시 (requestAccountDeletion · onCall)
 │    users.status='pendingDeletion' · deletedAt · purgeAt(+30d) · deletionReason
 │    reviews / photos / favorites .isHidden = true
 │    clubs.rating · reviewCount · favoriteCount 감산
 │    Auth 계정 disabled = true
 │
 └─▶ 30일 후 (purgeDeletedUsers · 매일 KST 04:30)
      Firestore 문서 + nicknames/{key} 예약 회수 + Storage 파일 + Auth 유저 완전 삭제
```

| 결정 | 이유 |
|------|------|
| **Auth 유저를 즉시 지우지 않고 `disabled`로** | 소셜 uid는 `kakao:{id}`로 **고정**이라 Auth에서 지우면 재로그인 시 **같은 uid가 다시 만들어져 보관 중 데이터에 붙는다**. `disabled`면 `signInWithCustomToken`이 `auth/user-disabled`로 거부되고, 앱의 `isSessionRevokedCode`가 그 코드를 이미 처리해 **다른 기기 세션도 다음 실행 때 자동 정리**된다(앱 추가 작업 0) |
| `deletedUsers` 컬렉션으로 옮기지 않는다 | 하위 컬렉션(`searchHistory`)까지 통째로 이사시켜야 하고, 파기 전까지 uid 소유권 판정이 두 컬렉션으로 갈라진다. **제자리 soft delete**가 단순하다 |
| **집계 감산 주체는 `requestAccountDeletion` 하나** | `isHidden=true` 세팅은 문서 update라 `onReviewUpdated`가 발화한다. 거기서 또 재계산하면 이중 감산 → 트리거에 가드를 단다. 가드가 없으면 파기 때 **두 번 깎여 음수**가 된다 |
| `searchLogs`는 건드리지 않는다 | TTL 14일이라 30일 시점엔 이미 사라진 뒤다. `userId`로 지우려면 인덱스를 새로 만들어야 하는데 얻는 게 없다 |
| 멱등 | 이미 `pendingDeletion`이면 기존 `purgeAt`을 반환하고 종료. 중간 실패 후 재호출해도 안 숨겨진 것만 이어서 처리 |
| 파기는 회차당 50명 | 한 명이 실패해도 로그만 남기고 다음으로 — 한 명 때문에 배치가 죽지 않게. 실패한 uid는 다음 회차에 다시 잡힌다 |

**트리거 가드**

| 함수 | 가드 |
|------|------|
| `onReviewUpdated` | `before.isHidden !== after.isHidden`이면 즉시 return (이미 숨겨진 리뷰의 별점 수정도 return) |
| `onReviewDeleted` | 삭제된 문서가 `isHidden === true`면 즉시 return |
| `onFavoriteDeleted` | 동일 |

**쓰기 경로도 `isHidden: false`를 같이 써야 한다** — `ReviewModel.toFirestore()`와 `firebase_favorite_datasource.addFavorite`에 들어 있다. 빠뜨리면 목록 쿼리(`where isHidden == false`)가 못 잡아 **새 리뷰가 조용히 사라진다**.

**인덱스 (신규 3 + fieldOverrides 2)**

```
users   COLLECTION       (status ASC, purgeAt ASC)        # purge 스케줄 조회
reviews COLLECTION       (isHidden ASC, createdAt DESC)   # 클럽 리뷰 목록
photos  COLLECTION       (isHidden ASC, createdAt DESC)   # 사진 탭
reviews COLLECTION_GROUP (userId ASC, createdAt DESC)     # 기존 재사용 (내 리뷰 관리)

# fieldOverrides (컬렉션 그룹 단일 필드)
reviews.userId  COLLECTION + COLLECTION_GROUP
photos.userId   COLLECTION + COLLECTION_GROUP
```

> `fieldOverrides`가 필요한 이유 — Firestore가 자동으로 만들어 주는 단일 필드 인덱스는 **컬렉션 스코프뿐**이다. 탈퇴 함수의 `collectionGroup('reviews').where('userId','==',uid)`(orderBy 없음)는 **컬렉션 그룹 스코프** 단일 필드 인덱스를 요구한다. 필드를 override 하면 기본 인덱스가 사라지므로 COLLECTION 스코프도 함께 적어 둔다.

**Rules 변경**

| 경로 | 변경 |
|------|------|
| `clubs/../reviews` | read: `resource.data.get('isHidden', false) == false` (기존 무조건 read → 조건부) + update 금지 키에 `isHidden` 추가 |
| `clubs/../photos` | read 동일 (photos엔 update 규칙 자체가 없음) |
| `users/{uid}` | update 금지 키에 `status`·`deletedAt`·`purgeAt` 추가 |
| `favorites` | 그대로 — `create`·`delete`만 있고 update 규칙이 없어 클라가 `isHidden`을 못 건드린다 |

- `isHidden` 클라 수정을 막는 이유 — 유저가 자기 리뷰의 `isHidden`을 직접 켜면 목록에서는 사라지는데 `reviewCount`·`ratingSum`은 그대로 남아 **평점이 영구히 어긋난다**
- ⚠ `resource.data.isHidden != true`로 쓰면 안 된다 — Rules에서 **없는 필드에 직접 접근하면 평가가 에러로 떨어져 거부**되므로 백필 전 문서가 통째로 막힌다

**백필** — `scripts/backfill_is_hidden.js` (2026.08.17 실행: reviews 1634 + photos 3222 + favorites 9 = **4865건**). 문서마다 PATCH가 아니라 `documents:commit`으로 500건씩 묶어 **요청 10회**로 끝낸다. 재실행 시 전부 skip(멱등).

#### 9.2.1 보관 기간 내 재로그인 = 복구

별도의 '탈퇴 철회' 버튼을 두지 않았다 — **로그인이 곧 복구**다. 되돌아온 사용자가 하는 행동은 어차피 로그인이고, 철회 화면을 따로 만들면 탈퇴 대기 계정에게만 보이는 로그인 앞 단계를 하나 더 유지해야 한다.

```
로그인 시도 (kakao / naver / phone)
 ├─▶ restorePendingDeletionOnLogin(uid)  # Custom Token 발급 전
 │    status != 'pendingDeletion'  ─▶ 아무것도 안 함 (restored=false)
 │    purgeAt 없음 · purgeAt <= now ─▶ failed-precondition (복구 안 함)
 │    그 외(보관 기간 안)          ─▶ 복구:
 │        reviews/photos/favorites.isHidden = false
 │        clubs.rating · reviewCount · favoriteCount 가산
 │        Auth 계정 disabled = false
 │        users.status='active' · deletedAt · purgeAt · deletionReason 삭제
 └─▶ Custom Token 발급 → 앱 signInWithCustomToken → 홈
```

| 결정 | 이유 |
|------|------|
| 토큰 발급 **전에** 복구 | Auth가 `disabled`인 채 토큰을 주면 앱의 `signInWithCustomToken`이 `auth/user-disabled`로 거부된다 |
| `purgeAt`이 지났으면 안 살린다 | 되살려도 그날 새벽 `purgeDeletedUsers`가 지운다. 이때 `purgeAt`을 **null로** 보내는 것도 의도 — 이미 지난 날짜를 "그날부터 가입 가능"이라 안내하면 거짓말 |
| 상태 필드를 **맨 마지막에** 지움 | 중간에 실패하면 `pendingDeletion`이 남아 다음 로그인이 처음부터 다시 시도한다. 각 단계가 `isHidden==true`인 문서만 손대므로 재실행해도 **이중 가산 없음**(숨김 쪽과 대칭) |
| 가산 주체도 함수 하나 | `isHidden`을 false로 되돌리는 것도 update라 `onReviewUpdated`가 발화하지만, 그 트리거는 **양방향 전이를 모두 건너뛰게** 돼 있어 그대로 재사용된다 |
| Storage 손댈 것 없음 | 탈퇴는 파일을 지우지 않고 숨기기만 했다 |

`checkPhoneDuplicate`를 같이 고치지 않으면 복구까지 도달하지 못한다 — 본인인증 경로는 로그인 전에 번호 주인을 먼저 묻고, 예전 규칙에선 본인이어도 `sameAccount=false`라 화면에서 먼저 막혔다. 이제 본인 + 파기 전이면 `sameAccount=true`·`pendingDeletion=false`·`restorable=true`로 통과.

**배포 짝은 자유** — 서버만 먼저 내보내도 구앱은 새 필드를 무시하고 복구된 계정으로 그냥 로그인된다(안내 토스트만 없음). 앱만 먼저 내보내도 구서버가 `restored`·`restorable`을 안 주므로 false 폴백 → 예전처럼 차단될 뿐이다.

#### 9.2.2 구 `deleteUser` 함수 제거 (2026.08.17)

소스에선 `bb2fb34`에서 이미 빠졌는데 **배포본만 살아 있었다**. users 문서·Storage·Auth를 **즉시 하드 삭제**하고 리뷰·사진·찜은 남겨 고아 데이터를 만드는, 30일 보관 요구와 정면으로 어긋나는 경로. 호출부·최근 30일 호출 로그 모두 0이라 제거. **탈퇴 경로는 `requestAccountDeletion` 하나뿐이다.**

### 9.3 프로필 수정 — 닉네임 · 프로필 사진

#### 고친 문제는 '실명 노출'이다

`users.name`은 본인인증으로 받은 **실명**인데 그게 그대로 표시 이름으로 쓰이고 있었다.

- `ProfileEditScreen` 입력칸 라벨은 '닉네임'인데 실제로 읽고 쓰는 건 `user.name` — **사용자가 자기 실명을 편집 중**
- `review_viewmodel` · `inquiry_viewmodel`이 `user?.name`을 `userName`으로 비정규화해 저장
- 클럽 상세 리뷰 카드가 그 `userName`을 다른 사용자에게 그대로 보여준다(아바타 첫 글자도 실명 첫 글자)

즉 **리뷰를 하나 쓰면 실명이 공개된다.** 닉네임 기능은 '있으면 좋은 것'이 아니라 **이 노출을 끊는 작업**이다.

#### 구조

```
앱 (ProfileEditScreen)
 ├─ 사진 고르기 → Storage 업로드  users/{uid}/profile_{millis}.jpg
 │                                  # Rules: 본인만 · 5MB · 이미지만 (기존 그대로)
 └─ updateUserProfile(nickname, photoUrl)   # onCall
      │
      ▼
  Cloud Functions ── 트랜잭션 ──┬─ nicknames/{newKey} create   # 있으면 already-exists
                                ├─ nicknames/{oldKey} delete
                                └─ users/{uid} update          # nickname · profileImageUrl
```

**트랜잭션 순서** (Admin SDK — 읽기 먼저, 쓰기 나중)

```
1. users/{uid} get                  # 없으면 failed-precondition
2. nicknames/{newKey} get
   ├─ 있고 uid ≠ 나 → already-exists
   └─ 있고 uid = 나 → 이미 내 것 (예약 create 생략)
3. nicknames/{newKey} create { uid }
4. nicknames/{oldKey} delete        # oldKey ≠ newKey 일 때만 — 같으면 방금 만든 걸 지운다
5. users/{uid} update { nickname, profileImageUrl?, updatedAt }
```

| 결정 | 이유 |
|------|------|
| **유일성을 클라에 맡길 수 없다** | Rules로 `nicknames/{key}`에 create만 열면 "이미 있으면 실패"까지는 공짜로 얻지만, 예약과 `users.nickname`이 맞는지는 Rules가 검사할 수 없다 — 트랜잭션 안의 `get()`은 같은 커밋의 다른 쓰기를 보지 못한다. 그래서 **예약만 하고 문서는 안 바꾸는 선점(squatting)**도, **예약 없이 문서만 바꾸는 유일성 우회**도 못 막는다 |
| `nicknames`는 클라에게 **아예 안 보인다** | read까지 막는다 — 존재 여부를 물어볼 수 있으면 **닉네임을 열거**할 수 있다. 앱은 이 컬렉션의 존재를 모른 채 `already-exists`만 받는다 |
| 사진도 같은 함수가 쓴다 | 따로 쓰면 한쪽만 저장되는 상태가 생긴다. 사진만 바꿀 때도 함수를 타므로 저장 경로가 하나 — 분기를 두면 "사진만 바꿨을 때만 나는 버그"가 생긴다 |
| 사진 URL을 **서버가** 검증 | 넘어온 URL이 `users/{uid}/` 아래를 가리키는지 코드로 확인. Rules 정규식으로 하면 퍼센트 인코딩 때문에 깨지기 쉽고, 깨지면 저장이 조용히 403이 된다 |
| 변경 주기 제한 없음 | 필요해지면 `nicknameUpdatedAt`을 두고 **함수 안에서** 판정 — Rules가 아니라 함수라 조건을 바꿔도 규칙 재배포가 불필요 |
| 파일명에 **타임스탬프** | `profile.jpg`로 덮어쓰면 URL이 그대로라 이미지 캐시·CDN이 옛 사진을 계속 보여준다("바꿨는데 안 바뀐다" — 앱을 지웠다 깔아야 고쳐지는 종류) |
| 옛 파일은 저장 **성공 후** 삭제 | 먼저 지우면 함수 호출이 실패했을 때 사진만 사라진 계정이 남는다. 삭제 실패는 `deleteFileByUrl`이 삼킨다(문서는 이미 갱신됐으니 저장을 실패로 뒤집으면 안 된다) |
| 업로드 전 `maxWidth: 720` | 92px 원형 아바타에 3배수를 줘도 276px이면 충분. 원본을 그대로 올리면 **5MB 상한에 걸려 조용히 403** |
| 크롭 UI 안 만든다 | `MyAvatar`가 `ClipOval` + `BoxFit.cover`라 이미 가운데가 원형으로 잘려 보인다 |

#### 닉네임 규칙 — 서버가 단일 소스

| 항목 | 값 | 이유 |
|------|-----|------|
| 길이 | 2 ~ 12자 | 리뷰 카드·마이페이지 프로필이 한 줄에 담는 폭. 넘기면 ellipsis로 잘려 누군지 알 수 없다 |
| 허용 문자 | `^[가-힣a-zA-Z0-9]{2,12}$` | 공백을 막으면 앞뒤 trim만으로 정규화가 끝난다 |
| 자모 단독 | 자동 배제 | `[가-힣]` 범위 밖이라 `ㅋㅋ`·`ㅇㅇ`가 그냥 걸러진다 |
| `_` | **금지** | 닉네임이 곧 문서 ID라 `__foo__`가 Firestore **예약 ID 패턴**에 걸린다. 한글·영문·숫자만 받으면 `/`·`.`도 애초에 못 들어온다 |
| 중복 | 불가 | `nicknames/{key}` 예약이 강제 |
| 금칙어 | 서버 최소 목록 | '운영자'·'관리자'·'vybe' 같은 사칭 어휘만. **서버에 둔다** — 앱에만 두면 함수를 직접 부르는 것으로 우회된다 |

**랜덤 생성기는 서버에만** — 형식 `{앞말}바이버{1000~9999}`(예: `신나는바이버4821`). 앞말은 클럽 단어 40개(춤·플로어 20 + 에너지·열정 20), 조합 **40 × 9000 = 36만**. 충돌 시 최대 5회 재시도.

> ⚠ 앞말은 전부 **4자 이하**여야 한다 — 몸통 `바이버`(3) + 숫자(4)와 합쳐 최대 11자로 상한 12에 1자 여유. 5자 단어를 넣으면 배정된 닉네임이 규칙을 넘어서고 **사용자가 자기 닉네임을 다시 입력할 수 없게 된다**(입력칸이 12자에서 끊긴다). 표가 서버에만 있어 눈으로는 안 잡히므로 `test/nickname_test.dart`가 `nickname.ts`의 `CLUB_WORDS`를 직접 파싱해 길이·문자·금칙어를 검사한다.

> ⚠ **띄어쓰기 없이 붙여 쓴다** — 공백을 허용하면 정규화가 복잡해지고(중간·연속 공백) 상한도 13자로 늘려야 한다. 뒤 4자리가 구분자 몫을 하므로 단어 수가 적어도 되고, 겹치지 않는 것은 예약이 강제한다.

앱은 형식만 복사해 둔다(`core/utils/nickname.dart`) — 서버 왕복을 기다렸다 빨간 글씨를 보여주면 입력이 답답하다. 한글 IME **조합 중 자모**(`새벽ㅇ`)는 오류로 띄우지 않는다(한 글자 칠 때마다 빨간 글씨가 번쩍인다). 저장 버튼은 그대로 막혀 있다.

#### 가입 흐름에서의 위치

```
본인인증 완료
 ├─ 1. setUserProfile()      users/{uid} create   # createdAt 은 여기서만 확정된다
 ├─ 2. updateUserProfile()                        # 인자 없음 = 랜덤 닉네임 배정 + 예약
 └─ 3. 가입완료 화면 → 홈
```

- **2번이 실패해도 가입은 막지 않는다** — 이미 계정은 만들어졌다. 닉네임 없는 짧은 창에는 중립 라벨(`VYBER`)을 보여주고 다음에 프로필 수정에서 저장할 때 다시 배정된다. 여기서 홈 진입을 막으면 네트워크가 잠깐 흔들린 사용자가 **가입 마지막 단계에 갇힌다**
- **배정을 로그인 3종 함수에 넣으면 안 된다** — 신규 유저는 그 시점에 users 문서가 없다(본인인증 뒤 `setUserProfile`이 만든다). 닉네임을 쓰겠다고 여기서 문서를 미리 만들면 `setUserProfile`의 `exists` 분기가 뒤집혀 **`createdAt`이 영영 안 써진다** — 이 프로젝트가 이미 한 번 겪은 버그다

#### 닉네임을 바꾸면 옛 리뷰·문의의 이름은?

`users`는 본인만 읽을 수 있다 → **남의 리뷰 작성자 이름을 users에서 조인해 오는 건 Rules상 불가능**하다. `reviews.userName`·`inquiries.userName` 비정규화는 선택이 아니라 필수.

| 안 | 내용 | 판단 |
|----|------|------|
| **A (채택)** | 옛 문서는 그때의 닉네임 유지. 새로 쓰는 것만 새 닉네임 | 비용 0. 게시 시점 기록으로도 자연스럽고, 본인의 '내 리뷰 관리'는 작성자 이름을 아예 안 보여줘 어긋남을 겪는 자리가 없다 |
| B | `updateUserProfile` 안에서 `collectionGroup('reviews')` 배치 update | 보류. 변경 1회당 리뷰 수만큼 write가 나가 변경 주기 제한이 같이 필요해진다 |

프로필 사진은 리뷰에 비정규화하지 않는다 — `reviews.userPhotoUrl`을 넣으면 사진을 바꿀 때마다 옛 리뷰가 옛 사진을 들고 있는 같은 문제가 하나 더 생긴다.

#### 탈퇴와의 상호작용

| 시점 | 예약(`nicknames`) 처리 | 이유 |
|------|------------------------|------|
| `requestAccountDeletion` | **그대로 둔다** | 보관 기간 안에 복구되는데 예약을 풀면 그사이 남이 가져간 닉네임을 되찾을 수 없다. 복구는 '원래대로'여야 한다 |
| `purgeDeletedUsers` | **회수한다** | 안 지우면 아무도 쓰지 않는 닉네임이 영원히 잠긴다. **users 문서를 지우기 전에** `nickname`을 읽어 둘 것 — 순서를 뒤집으면 key를 알 방법이 없다 |
| `restorePendingDeletionOnLogin` | 변경 없음 | 예약을 안 건드렸으므로 되살릴 것도 없다 |

#### 기존 유저 — 백필하지 않는다 (확정)

- `nickname`이 없는 계정은 앱이 중립 라벨 `VYBER`로 표시
- 그 계정도 프로필 수정에서 저장하면 그때 배정된다
- 그때까지 쓴 리뷰·문의는 `userName`이 빈 값이라 리뷰 카드에 '익명'으로 뜬다
- ⚠ **폴백을 `name`으로 두면 안 된다** — 고치려는 문제(실명 노출)를 그대로 남기는 셈이다

#### 구현하면서 설계와 달라진 곳 4건

| # | 설계안 | 구현 | 이유 |
|---|--------|------|------|
| 1 | 기본 아바타 = 보라 그라데이션 + 닉네임 첫 글자 | 글자 없는 **중성 실루엣** | 요구사항. 부수 효과로 아바타에서도 이름이 사라져 실명 노출 경로가 통째로 없어졌다 |
| 2 | `invalid-argument` 하나 | `details.field`에 `'nickname'` \| `'photo'` | 사진 URL 거부를 닉네임 입력칸 아래에 붙이면 엉뚱한 곳을 고치게 된다. 메시지 문구로 갈라내면 문구를 고칠 때 깨지므로 **코드로** 준다 |
| 3 | 사진 시트 안내 10MB | **5MB** | `storage.rules` 상한. 시안대로 쓰면 6MB 사진이 조용히 403 |
| 4 | '닉네임은 30일 지나야 다시 변경' | 문구를 **뺐다** | 서버에 그 제한이 없다 — 없는 규칙을 안내하면 거짓 정보 |

**백엔드 영향**: Functions 신규 1개(15→16) + `purgeDeletedUsers`에 예약 회수 추가 · 컬렉션 `nicknames` 신규 · `users.nickname` 신규 · 인덱스 **없음**(문서 ID로만 접근) · Firestore Rules 금지 키 확대 + `nicknames` 전면 차단 · **Storage Rules 변경 없음**(`users/{uid}/**` 규칙이 파일명 변경·삭제를 이미 덮는다) · Algolia 영향 없음 · 마이그레이션 없음.
**비용**: 가입 시 함수 1회(read 1 + write 2) · 프로필 저장 시 함수 1회(read 1 + write 2~3) + Storage 업로드 1(사진을 바꿨을 때만).

### 9.4 리뷰 작성 · 평점 집계

```
리뷰 작성 (clubs/review_write_screen.dart)
 │ 별점 0.5 단위 · 추천 태그 칩 → tags · 사진 최대 4장 · 본문 500자
 ├─▶ image_picker → Storage reviews/{clubId}/{reviewId}/{index}.{ext}
 ├─▶ clubs/{clubId}/reviews/{reviewId} 생성      # isHidden: false 반드시 포함
 └─▶ onReviewCreated 트리거
      ratingSum += rating · reviewCount += 1 · rating = ratingSum / reviewCount
```

| 이벤트 | 트리거 | 동작 |
|--------|--------|------|
| 생성 | `onReviewCreated` | `increment()`로 `ratingSum`·`reviewCount` 증가 후 `rating` 재계산 |
| 수정 | `onReviewUpdated` | `ratingSum += (new - old)`. `isHidden` 전이거나 이미 숨겨진 리뷰면 skip |
| 삭제 | `onReviewDeleted` | 감산 후 `reviewCount == 0`이면 `rating = 0`. `isHidden==true`면 skip |

- `rating`·`ratingSum`·`reviewCount`는 **클라가 절대 쓰지 않는다**. 증감은 `FieldValue.increment()`(동시 요청 정합성), `rating` 계산은 트랜잭션. Rules에서도 클럽 문서 쓰기는 어드민 전용
- 업로드 순서 — **`reviewId` 선발급 → Storage 업로드 → 문서 생성**. 업로드가 실패하면 문서가 안 생겨 '안 보내졌다'가 정확하게 전달된다
- 마이페이지 '내 리뷰 관리'는 `collectionGroup('reviews') where userId== orderBy createdAt desc`. **여기엔 `isHidden` 필터를 걸지 않는다** — 숨김은 작성자 탈퇴 때만 붙는데 탈퇴하면 그 화면에 못 들어온다. 걸면 3필드 인덱스만 늘어난다
- 리뷰 수정은 작성 화면을 재사용한다
- 리뷰 목록은 **1회 get**(스트림 아님). invalidate는 **호출부**에서 — `reviewViewModelProvider`는 autoDispose인데 작성 화면이 `ref.read(.notifier)`로만 잡아 await가 끝나면 이미 dispose돼 `ref.mounted == false`라 ViewModel 안의 invalidate가 죽은 코드가 된다

### 9.5 찜 · 집계 카운터

`favorites`는 **top-level** 컬렉션 — 유저 하위가 아니라 최상위에 둔 이유는 `userId`·`clubId` **양방향 조회**를 같은 컬렉션에서 처리하기 위함.

| 동작 | 클라 | 서버 |
|------|------|------|
| 찜하기 | `favorites` 문서 생성 (`isHidden: false` 포함) | `onFavoriteCreated` → `favoriteCount += 1` |
| 찜 해제 | 문서 삭제 | `onFavoriteDeleted` → `-= 1` (0 미만 방지). `isHidden==true`면 skip |

찜에는 **update 규칙이 아예 없다** — `create`·`delete`만 허용하므로 클라가 `isHidden`을 건드릴 경로가 원천적으로 없다. 리뷰처럼 금지 키를 나열할 필요가 없어진 구조.
인덱스: `favorites(userId ASC, createdAt DESC)`.

- 한국어는 **부분 일치**(실측 `테이션` → `클럽 스테이션`)

#### 한글 조합 중 자모 (2026.08.24)

엔진은 **완성형 음절만** 인덱싱한다. 타이핑 중 마지막 글자로 남는 단독 자모(`ㅇ` U+3147)를 그대로 던지면 AND 매칭이 결과를 통째로 0건으로 만든다 — 실측 `홍대` 57건 · `홍대 어` 4건 → **`홍대 ㅇ` 0건** (`removeWordsIfNoResults: 'none'`이라 안 지워진다).

→ `searchClubsPage`가 검색어를 **엔진에 던질 부분 / 초성으로 거를 자모**로 쪼갠다 (`core/utils/hangul_search.dart` — 순수 함수, 테스트 15건).

- 자모가 있으면 후보를 `pageSize * 8`(상한 80) 받아 **이름 초성**으로 거르고, 초성이 앞쪽에서 걸린 곳을 먼저 정렬(`홍대 ㅇ` → 어썸레드가 '홍대 클럽 나인'보다 위)
- 쌍자음은 홑자음으로 눕힌다(`ㅅ`로도 '썸'이 걸린다). 초성이 못 되는 모음·겹받침 자모는 버린다
- ⚠ **처리 위치는 `searchClubsPage` 한 곳** — 검색 3경로(연관 검색어 · 검색 결과 · 주변 지도)가 전부 여기를 지난다. 화면마다 따로 손대면 같은 검색어가 화면마다 다르게 걸린다
- ⚠ 자모를 걸렀을 땐 `totalCount`에 엔진 `nbHits`(거르기 전 수)를 **쓰지 않는다** — '검색결과 N'이 목록보다 큰 숫자를 말하게 된다

#### 그 외

- 진입점은 `ClubRepositoryImpl.searchClubsPage` 하나 — viewmodel·화면은 엔진 무관. cursor = Algolia 페이지 번호(int, 0부터)
- 비활성 클럽 제외는 hit의 `isActive` 값으로(폴백 경로에선 조인 후 확인). **Algolia `filters`는 `attributesForFaceting` 미선언 속성이면 조용히 0건이라 사용 금지**
- Indexable Fields를 바꾸면 기존 문서는 자동 반영 안 됨 → `node scripts/reindex_clubs.js`. 단 **Extension 업데이트 자체는 전체 재색인을 동반한다**(`DO_FULL_INDEXING=true`) — 설정만 고치면 수동 touch가 불필요
- 키 규칙: 앱에는 **Search-Only 키만**. Admin/Write 키는 Extension(서버)에서만 — 앱 번들은 뜯어볼 수 있다
- `.env`에 ALGOLIA 키가 없으면 검색 결과 빈 값(폴백 없음)

#### ⚠ 배포된 설정이 문서와 달라져 있던 적이 있다 (2026.08.21 발견)

배포본 `FIELDS`에 `reviewCount`·`entryFeeMax`·`operatingHours`·`isVybeRecommended`·`isNonSmoking`·`location` **6개가 빠져 있었고**(= 2026.07.31 '조인 제거' 설정이 실제로는 반영된 적이 없음), 그동안 검색은 내내 `complete=false` → `getClub` 조인 폴백으로 돌고 있었다. **화면이 멀쩡해서 티가 안 난다** — 조용히 read 비용만 낸다.

### 9.7 클럽 카탈로그 캐시

목록 화면이 화면마다 따로 쿼리를 날려 한 세션에 `clubs` read가 **500~700**이었다. 지금은 `ClubRepositoryImpl`이 `clubs(isActive==true)` **164건을 세션당 한 번** 읽어 들고 있는다.

| 항목 | 내용 |
|------|------|
| provider | `clubRepositoryProvider`는 **keepAlive** — 화면을 옮겨도 캐시가 산다 |
| TTL | `ClubRepositoryImpl.catalogTtl` = **10분**. 지나면 다음 목록 호출이 다시 읽는다 |
| 동시 진입 | `Future`를 들고 있어 동시 진입(홈 두 섹션 + 주변 탭)도 **1회**. 실패한 Future는 즉시 버린다(TTL 동안 전부 죽지 않게) |
| 메모리 필터 | `getClubsNearby`(haversine · 가까운 순) · `ByArea` · `ByGenre` · `FreeEntry` · `TimedFreeEntry` · `NonSmoking` · `ServiceDrink` |
| 남은 쿼리 | `firebase_club_datasource`에는 `getActiveClubs` · `getClub` · `getClubsByIds` · info · menus · photos · tableLayout 만 남음 |
| 단건 조회 | `getClub`은 **여전히 새로 읽는다**(상세 화면). 조인용은 `getClubCached` — 찜 탭·내 리뷰가 카탈로그에서 꺼내고, 없는 id(비활성·신규)만 `getClub`으로 떨어진다 |

- ⚠ **당겨서 새로고침 훅은 없다** — 10분 TTL이 유일한 갱신. 필요해지면 `_catalog = null` 한 줄을 되살려 `RefreshIndicator`에 물린다
- ⚠ `clubs.location.geohash` 필드는 남아 있지만 **앱은 더 이상 안 읽는다** — 반경 판정은 haversine. geohash 범위 쿼리는 2026.09.15 제거(`GeohashUtils`엔 `haversineKm`만 남음)

### 9.8 시간대별 무료입장

요구는 둘 — ① 일정 시간대에는 입장비가 무료인 클럽이 있다 ② 그 시간이 아니면 일반 입장비. 기존 스키마엔 시간축이 없어 `entryFeeMin == 0` 하나로 '무료'를 표현하고 있었고 그 값은 켜면 24시간 무료다. **필드를 하나 더 얹는 게 아니라 의미를 갈라야 했다.**

| 결정 | 이유 |
|------|------|
| `entryFeeMin`·`entryFeeMax`는 **평상시(유료) 입장비**로 의미 고정 | 요구 ②가 곧 이 필드다. 무료 여부를 여기 섞으면 "무료 시간이 끝나면 얼마인가"를 저장할 자리가 사라진다 |
| 무료는 `freeEntry` 정책 객체가 **단독 소유** | 상시 무료 · 시간대 무료 · 무료 없음을 한 필드에서 구분. 조건 코멘트도 같이 |
| 지금 무료인지는 **클라 순수 함수**가 판정, 쿼리는 불리언 하나만 | Firestore는 "요일 × 시:분 × 자정 넘김"을 쿼리할 수 없다. 서버 쿼리는 *무료 정책을 가졌는가*까지만 좁히고 시각 판정은 메모리에서 |
| `type`을 `windows` 유무로 대신하지 않는다 | '상시 무료'와 '시간대 무료인데 창을 아직 안 넣었다'가 구분돼야 한다. 후자를 상시 무료로 읽으면 **유료 클럽이 무료로 노출된다** |
| `isFreeEntry`를 트리거로 만들지 않는다 | `clubs` write가 Algolia 동기화를 다시 태워 쓰기·색인이 2배 — `freeEntry`를 쓰는 쪽(seed·어드민)이 **한 쌍으로** 쓴다 |

> ⚠ **timed 클럽의 `entryFeeMin`을 0으로 만들지 말 것** — ① 무료 시간이 끝나도 화면이 계속 '무료'로 뜨고 ② 구버전 앱·미변경 경로(`entryFeeMin == 0` 판정)가 상시 무료로 오인한다.

#### 판정 로직 (`data/models/free_entry_policy.dart` — 순수 Dart, Firebase 의존 0)

```dart
class FreeEntryStatus {
  final bool isFreeNow;              // 지금 이 순간 무료인가
  final FreeEntryWindow? active;     // 지금 걸린 창 (끝나는 시각 표기용)
  final DateTime? nextStartAt;       // 다음 무료 시작 — 없으면 null
}
FreeEntryStatus statusAt(DateTime now)
```

| 규칙 | 내용 |
|------|------|
| 경계 | `start` 포함 · `end` 미포함 — `DayHours.isCurrentlyOpen`과 동일 |
| 자정 넘김 | `end <= start`면 다음 날로 이어진다. **창은 시작 요일에 속한다** — 금 23:00~02:00은 토요일 01:00도 무료 |
| 전날 검사 | 그래서 판정은 **오늘 창 + 어제 창**을 같이 본다. 오늘 것만 보면 새벽 무료가 통째로 사라진다(영업시간과 똑같은 함정) |
| 다중 창 | 한 요일에 창이 여러 개 가능. 겹치면 합집합 |
| 시계 | 기기 로컬 시간(KST 가정). 서버 시각을 안 쓰는 이유 — 판정마다 왕복을 넣을 이유가 없고, 기기 시계가 틀리면 영업중 뱃지가 이미 틀린다 |

- **'지금 무료' 뱃지는 영업 중일 때만** — 휴무일·창 설정 실수로 문 닫은 클럽이 무료 창에 걸릴 수 있다. 문 닫은 클럽에 '지금 무료'는 거짓 정보
- **테스트에서 잡힌 실제 버그** — `start == end`거나 시각 문자열이 깨진 창(`"22:99"`·`"25:00"`)이 **24시간 무료로 평가됐다**. 유료 클럽이 종일 무료로 노출되는 방향이라 `FreeEntryWindow.isValid`로 막았다. 진짜 24시간 무료는 `type: 'always'`로 쓴다

#### 화면 문구 매트릭스

| 상태 | 카드 / 상세 표기 |
|------|------------------|
| timed · 창 안 · 영업 중 | **지금 무료 · 01:00까지** (라임 액센트) |
| timed · 오늘 창이 남음 | **22:00부터 무료** + 평상시 요금 병기 |
| timed · 오늘 창 없음 | 평상시 요금 + **금·토 22시 무료** |
| always | **무료입장** |
| none | 평상시 요금만 |

- 입장비 무료 페이지 정렬 — '지금 무료'를 맨 위, 그다음 `nextStartAt`이 가까운 순. 낮에 들어와도 목록이 비지 않고 "오늘 몇 시부터"가 보인다
- 검색 필터 '무료입장' 칩은 `isFreeEntry` 기준 — **'지금 무료'로 좁히지 않는다**. 낮에 눌러 0건이 나오면 필터가 고장 난 것처럼 읽힌다
- 시각 표기 문구는 `presentation/common/free_entry_labels.dart` 한 곳(홈·상세·페이지 공유) — 두 화면이 같은 클럽을 다르게 말하면 안 된다

#### 클럽 상세 도형 (`free_entry_timeline.dart`)

⚠ **Firestore에 시간대별 요금표는 없다** — 도형은 `operatingHours`(회차) × `freeEntry.windows` × `entryFeeMin`을 겹쳐 만든다(테스트 17건). 없는 요금 구간을 지어내지 않는다.

- 도형이 그리는 **회차(오픈~마감)**는 앵커로 고른다 — 무료 중이면 지금 회차, 아니면 다음 무료 창의 시작 시각이 든 회차. 앵커 회차에 무료 구간이 없으면 도형을 뺀다(다른 날로 몰래 건너뛰면 헤드 문구와 다른 날을 그린다)
- 칸 너비는 길이 비례지만 **최소 폭 52**를 보장하고 모자란 만큼 넓은 칸에서 뗀다. 현재 시각 마커도 **같은 너비 배열**로 계산해야 칸 경계와 안 어긋난다
- 디자인의 **'무료 시간 시작 전 알림 받기' 버튼은 뺐다** — 푸시 경로가 없어 눌러도 아무 일이 없다. '만석 시 조기 마감'·'신분증 지참' 두 줄도 대응 필드가 없어 뺐다

### 9.9 테이블 배치도 · 가격

클럽마다 홀 구조가 다르다. 지금까지 앱은 테이블 9자리를 **상수로 박아** 164개 클럽에 똑같은 배치도를 보여주고 있었다(`table_pricing_data.dart`). 이 문서가 그 상수를 대체한다 — 배치·가격·예약 조건을 클럽별로 저장하고 업주가 업주용 웹에서 직접 편집한다.

#### 위치는 정수 그리드 셀

층마다 `cols × rows` 격자를 두고, 테이블·구조물은 자기가 점유하는 **셀 사각형**(`col`·`row`·`colSpan`·`rowSpan`)만 저장한다.

| 항목 | 그리드(정수) — 채택 | 소수 좌표(0~1) |
|------|---------------------|----------------|
| 웹·앱 일치 | `col * width / cols` — **반올림 여지 없음** | 웹 0.1333 vs 앱 0.1334 미세 어긋남 |
| 캔버스 비율 | `cols / rows`로 자동 도출(셀 정사각) | `aspectRatio` 필드를 웹·앱이 따로 지켜야 함 |
| 겹침 | 셀 비교로 편집기가 **원천 차단** | 검증 어렵고, 겹치면 앱에서 글자가 뭉갠다 |
| 편집기 비용 | 셀 단위 스냅 — 픽셀 계산 불필요 | 드래그 좌표 변환·스냅·경계 처리 전부 필요 |
| 회전 | **개념이 없다**(축 정렬만) — 필드·렌더 코드 없음 | `rotation` + `Transform.rotate` 필요 |

**포기한 것** — 비스듬한 홀·대각선 배치·곡선 벽. 나이트클럽 배치도에 그 정밀도가 필요하지 않고, 필요해지면 `cols`를 올려 근사한다.

> ⚠ **열 최대 14 + 테이블 최소 2×2가 짝을 이뤄 탭 타겟 44px 하한을 보장한다** — 가장 좁은 흔한 기기(iPhone SE 375)에서 섹션 좌우 20.w + 캔버스 안쪽 8.w를 뺀 격자 폭 ≈321px ÷ 14열 ≈23px/셀 × 2칸 ≈**46px**(기준 폭 393에선 48px). **열을 더 늘리거나 캔버스 여백을 키우면 이 보장이 깨져 손가락으로 못 누르는 테이블이 생긴다** — 둘 다 셀 폭을 깎는다. 구조물은 탭 대상이 아니라 1칸을 허용한다.

#### 미니맵 비율 = `cols : rows`

셀이 정사각이므로 칸 수의 비가 곧 배치도 모양. 별도 `aspectRatio` 필드가 필요 없다.

| 결정 | 이유 |
|------|------|
| 비율 = 칸 수의 비 (별도 필드 없음) | 필드를 두면 웹·앱이 각자 지켜야 할 값이 하나 늘고, `cols/rows`와 어긋나면 셀이 정사각이 아니게 되어 **탭 타겟 계산이 무너진다** |
| 프리셋은 가로 칸을 유지하고 세로 칸만 맞춘다 | 둘 다 바꾸면 이미 놓아 둔 배치가 가로로도 밀려 대부분 '밖으로 나감'으로 막힌다 |
| 상한은 가로 칸에만 | 앱 칸 크기 = 폭 ÷ 가로 칸. 세로 칸은 미니맵이 세로로 길어질 뿐 칸 크기와 무관 |

#### 방 모양 — 격자 안에서 바닥을 깎는다 (`cells`)

클럽 홀이 직사각형인 경우가 오히려 드물다(ㄱ자, 계단 옆이 파인 형태). 격자는 바운딩 박스로 두고 그 안에서 실제 바닥만 `'1'`로 남긴다.

```
cols=4, rows=4 인 ㄱ자 방
  1 1 1 1      cells = "1111" + "1111" + "1100" + "1100"
  1 1 1 1      (길이 = cols * rows, 행 우선)
  1 1 · ·
  1 1 · ·      빈 문자열 = 직사각형 방 전체
```

| 결정 | 이유 |
|------|------|
| 격자를 없애지 않고 마스크만 얹는다 | 좌표계·탭 타겟·웹↔앱 일치가 전부 격자 위에 서 있다. 자유 폴리곤으로 바꾸면 그게 다 무너진다 |
| 빈 문자열 = 전체 | 대부분은 직사각형. 그때는 앱이 **둥근 카드**로 그린다 — 셀 단위 외곽선은 모서리가 각져 카드보다 거칠다 |
| 길이가 `cols*rows`와 다르면 **버린다** | 격자를 바꾸고 마스크를 안 고친 문서다. 어긋난 마스크로 그리면 엉뚱한 칸이 뚫려 배치도가 거짓말을 한다. 편집기는 격자를 바꿀 때 마스크를 같이 옮긴다(remap) |
| 전부 `'1'`·전부 `'0'`도 버린다 | 각각 '마스크 없음'과 같고, 바닥이 하나도 없는 층은 그릴 게 없다 |
| 채움은 이어 붙이고 **선은 경계 변에만** | 셀마다 사각형을 다 그리면 격자무늬로 보인다. 방 밖과 맞닿은 변에서만 선을 그어야 하나의 방 윤곽으로 읽힌다(`_FloorPlatePainter`) |
| 테이블은 방 안만, 구조물은 자유 | 테이블이 허공에 뜨면 **상품 정보가 거짓**이 된다. 벽·계단은 경계에 걸치는 게 자연스럽다 |
| 물건이 놓인 칸은 못 뺀다 | 빼면 그 물건이 허공에 뜬 채로 저장돼 앱에 그대로 나간다. 편집기가 막고 안내한다 |

#### 구조물 색은 타입마다 고정

`stage`(보라) · `dj`(핑크) · `dancefloor`(청록) · `bar`(앰버) · `entrance`(라임) · `restroom`(파랑) · `stairs`(회색) · `wall`(흰 반투명) · `etc`(무채색).

**업주가 못 바꾼다** — 클럽마다 무대가 다른 색이면 사용자가 배치도를 색으로 알아보는 학습이 통째로 무너진다. 클럽별로 다른 건 **등급(tier) 색뿐**이다.
정본은 `lib/data/models/table_layout_palette.dart`의 `kFixtureStyles`, 편집기의 `FX_STYLE`이 **같은 값**을 들고 있어야 한다.

#### 왜 문서 한 건인가 (테이블마다 문서 ✗)

| 결정 | 이유 |
|------|------|
| 층·구조물·테이블·등급을 한 문서에 | 배치도는 **통째로 편집되고 통째로 읽힌다**. 쪼개면 앱은 read N회, 웹은 저장이 원자적이지 않아 저장 도중 **반쯤 옮겨진 배치도**가 앱에 보인다 |
| 1MB 한도 걱정 없음 | 테이블 50개 + 구조물 15개여도 20KB 미만 |
| 쓰기는 문서 **전체 교체(set)** | 부분 update를 허용하면 지운 테이블·층이 남는다 |
| `schemaVersion`을 둔다 | 앱이 모르는 판(> 1)이면 렌더를 **포기**한다. 모르는 필드를 억지로 그리면 깨진 화면이 나온다 |

#### 색·타입은 키만, 금액은 숫자로

- `colorKey`(purple·blue·lime·pink·amber·gray)와 `fixture.type`은 **영문 키만** 저장 — 업주가 hex를 자유 입력하면 다크 배경에 안 보이는 색이 나오고, 앱 테마를 바꿀 때 전 클럽 문서를 손봐야 한다. 앱이 모르는 `fixture.type`은 조용히 버린다
- 구 상수는 `price: '100만'`, `minSpend: '1,000,000원'` **문자열**이었다. 업주가 `100만원`/`100만`/`1000000`을 제각각 입력하면 정렬·비교·필터가 전부 불가능 → **`price: 1000000`(원 단위 int)**. 표기는 `presentation/common/table_price_format.dart` 한 곳. **`0`은 무료가 아니라 '문의'** — 테이블은 공짜로 주는 상품이 아니다

#### 권한 — 파트너 커스텀 클레임

```
업주 계정 클레임 : { partner: true, clubIds: ["abc123", "def456"] }

Rules  clubs/{clubId}/tableLayout/{docId}
  read  : 누구나
  write : admin 또는 (partner == true && clubId in token.clubIds)
          + request.resource.data.clubId == clubId
          + schemaVersion is number
```

| 규칙 | 이유 |
|------|------|
| `is int`가 아니라 **`is number`** | 클라 SDK가 숫자를 double로 실어 보내면 `is int`는 업주의 **모든 저장을 거부**한다. 보안 경계가 아니라 형식 가드일 뿐이라 넓게 받고 실제 판정은 앱 파서가 한다 |
| `token.get('clubIds', [])`로 읽는다 | 클레임에 키가 없는 계정에서 직접 접근하면 Rules 평가가 에러로 떨어져 통째로 거부된다(`isHidden` 때와 같은 함정) |
| 셀 좌표·배열 원소는 Rules로 검증하지 **않는다** | Rules에는 **반복문이 없어** 배열 안 객체를 못 훑는다. 소유권·`clubId` 일치만 막고 값 검증은 파트너 웹 입력단 + 앱 파서가 한다 |
| 앱 파서가 격자 밖 값을 clamp | 격자를 나중에 줄였거나 잘못된 문서가 들어와도 화면 밖에 그리지 않는다. 1×1 테이블은 2×2로 키운다 |

> ⚠ **권한 회수는 즉시 반영되지 않는다** — 커스텀 클레임은 ID 토큰에 박혀 있어 `clubIds`에서 클럽을 빼도 기존 토큰이 만료될 때까지(**최대 1시간**) 쓰기가 통과한다. 계약 해지처럼 즉시 끊어야 하면 `revokeRefreshTokens` + Rules의 `auth_time` 검사가 필요하다.
> ⚠ 클레임 전체는 **1000바이트 제한** — 업주 한 명이 클럽 수십 곳을 갖는 구조가 되면 `clubs.ownerUids` + Rules `get()` 방식으로 옮겨야 한다(그때는 Rules get이 read 1회로 과금된다).

#### 앱 동작

| 상황 | 화면 |
|------|------|
| 배치도 없음 / 테이블 0자리 / 모르는 `schemaVersion` | 파서가 null → **섹션 자체를 뺀다**. 빈 카드는 '테이블 없음'과 구분이 안 된다 |
| 층 1개 | 층 탭 없음 |
| 층 2개 이상 | 층 세그먼트 탭. 층을 바꾸면 선택 테이블도 그 층 첫 자리로 옮긴다 — 안 그러면 하이라이트 없는 배치도 아래에 다른 층 카드만 떠 있다 |
| 테이블 없는 층 | 파서가 목록에서 뺀다 — 눌렀는데 빈 격자만 나오는 층 탭은 고장으로 보인다 |
| `isActive: false` 테이블 | 노출 제외(공사중·시즌). 그것뿐이면 섹션 전체가 사라진다 |

**셀 크기는 폭에서만 구한다** — `maxWidth / cols`. 높이로 따로 구하면 두 값이 미세하게 달라져 아래로 갈수록 도형이 어긋난다. **업주 웹도 같은 식을 써야 같은 그림이 나온다.**

#### 업주 웹이 지켜야 할 계약

- 저장은 문서 통째로 `set()` — **부분 update 금지**(원자성이 이 설계의 핵심)
- 테이블끼리 셀 겹침 금지. 구조물은 겹쳐도 된다(앱이 구조물을 먼저 그리고 테이블을 위에 얹는다)
- 격자 밖 금지 — `col + colSpan <= cols`, `row + rowSpan <= rows`
- 테이블 최소 2×2, 구조물 1칸 허용. `cols` 4~14, `rows` 4~32
- 테이블은 방 안에만 — `cells`로 도려낸 칸을 밟으면 앱에서 허공에 뜬다
- `cells` 길이는 항상 `cols × rows`. 격자를 바꾸면 마스크도 같이 remap
- 비율은 `cols : rows`로만. 별도 `aspectRatio` 필드를 만들지 않는다
- `id`는 층 안에서 유일. **기존 테이블 id를 바꾸지 않는다**
- 금액은 원 단위 정수만 · `schemaVersion: 1` 고정
- `cols`·`rows`를 줄일 때 밖으로 밀려나는 항목이 있으면 **저장을 막는다** — 앱은 clamp하지만 그 결과는 업주가 의도한 배치가 아니다

#### 업주용 웹 (`partner/`)

| 항목 | 내용 |

### 9.10 공연 일정 · 장르 페이지

**문서 1개 = (클럽 × 날짜 × 공연).** 같은 클럽이 여러 날 공연하면 doc이 여러 개 생긴다(`clubId` 동일, `date`·`startAt` 상이) — 이것이 **멀티-날짜 저장**의 핵심.

| 결정 | 이유 |
|------|------|
| **top-level** 컬렉션 (클럽 하위 아님) | DJ rail·hero가 "오늘 모든 힙합 클럽 공연을 시간순"으로 가져오는 **크로스-클럽 쿼리**다. 서브컬렉션이면 `collectionGroup`이 필요해진다 |
| `clubName`·`clubArea` 비정규화 | rail·hero에서 조인 없이 바로 표시 |
| `date`(YYYYMMDD) 문자열 버킷 | "오늘" 조회를 등호 하나로 끝낸다 |
| `live`·`lineup`을 클럽에 저장하지 않는다 | 오늘 공연 목록을 `clubId`로 머지해 도출 — **날짜가 지나면 자동으로 무효**가 된다. 저장하면 매일 정리해 줘야 한다 |
| 아티스트 별도 컬렉션 없음 | `artistName`·`artistType` 임베드. `artistType`이 rail 아이콘(Mic / Disc)을 가른다 |

**쿼리**: `genre== + date==<today> + isActive==true orderBy startAt asc` → hero = `isFeatured`만 / rail = 전체.

> ⚠ **`isActive`를 쿼리에서 빼면 안 된다 (2026.08.28 수정)** — 배포된 인덱스가 `(genre, date, isActive, startAt)`이라, `isActive` 없이 `orderBy startAt`만 걸면 정렬 필드 앞에 제약 없는 `isActive`가 끼어 **인덱스를 못 탄다**(`FAILED_PRECONDITION`). 뷰모델이 이 예외를 삼켜(그리드는 살려야 하므로) 힙합·EDM 둘 다 **공연 일정이 조용히 빈 화면**이었다. 전 문서가 `isActive: true`라(633/633) 쿼리에 넣어도 누락 없음.

**정리 — `cleanupPastPerformances` (매일 KST 04:00)**

`date`가 아니라 **`startAt` 기준**으로 지운다 — 공연은 `startAt` 후 최대 8시간 진행으로 가정(`PERFORMANCE_DURATION_HOURS`, 클럽 마감 ~06:00). `startAt < now - 8h`인 것만 삭제해 오늘 밤 새벽 공연·어제 이어진 공연을 보존한다. **날짜로 지우면 새벽 2시 공연이 사라진다.** 500개씩 배치 삭제.

**밤 시각 계산은 공용 `presentation/common/night_clock.dart` 하나** — 06시 미만은 +24h. 힙합 '오늘의 라인업'도 이걸 위임해서 쓴다(두 화면이 같은 공연을 다른 상태로 말하면 안 된다). **시작 후 60분 = 진행 중.**

**seed — `seed_performances_sep.js` (현행, 2026.08.28 실행)**

- 실행일~9/30, **장르 힙합·EDM 클럽 52곳만**(나머지 112곳은 공연 없음)
- 힙합은 `artistType` dj+rapper 혼합(2팀 이상이면 양쪽 최소 1팀), **EDM은 dj만**
- ⚠ 공연일은 **클럽 영업일 안에서만** — DB의 클럽이 전부 목·금·토만 열어서 '주 2일 휴무'를 달력 그대로 적용하면 문 닫은 날 공연이 잡힌다. 대신 **목·금·토 중 매주 랜덤 1일을 휴무**로 빼 주 2일 공연이 된다
- ⚠ 전 요일 영업인 예외 클럽 1곳 때문에 월·화·수·일이 후보일에 섞이면 휴무일 추첨이 아무도 안 여는 날에 걸려 무의미해진다 → **대상 클럽의 25% 이상이 여는 요일만** 후보로 본다
- 난수는 전부 `clubId`·날짜 해시 기반이라 **재실행해도 같은 결과**(멱등). `--dry` 확인만 · `--purge` 전삭제 후 재작성
- 실행 결과: 공연일 10일 / **doc 633개**(힙합 rapper 132 + dj 127, EDM dj 374) / hero `isFeatured` 30건

**세부 장르(`genreStyles`) 폐기 (2026.09.01)** — 값이 실제 조사 데이터가 아니라 `clubId` 해시로 만든 샘플이었고, 이걸 읽던 화면 3곳(힙합 라인업 장르 칩 · EDM 타임테이블 장르 필터 · 포스터 #태그)을 같이 걷어냈다. 포스터 #태그는 이제 `tags` → 없으면 `genre`. 지운 것 — Firestore `clubs.genreStyles` 22개 문서(`scripts/delete_genre_styles.js`) · `ClubModel.genreStyles` · `LineupItem.genres` · `EdmSet.style` · `kEdmAllStyles` · seed의 `STYLE_SETS`. **되살리려면 실 조사 데이터가 먼저다.**

### 9.11 배너 → 공지사항 상세

**배너마다 다른 광고 글을 앱 배포 없이 DB만으로 추가**하는 것이 목적. 광고 글은 `notices`에 같이 쌓아 배너가 내려간 뒤에도 공지 목록에서 다시 찾을 수 있게 했다(2026.08.24 통합).

```
홈 배너 탭
 ▼ banner_link_handler.dart            # linkType 분기 (라우팅 단일 지점)
 ├── "notice" ──▶ notices/{linkValue} doc 1건 get   # openNoticeDetail()
 │               ─▶ NoticeDetailScreen             # 공지 목록에서 여는 것과 같은 화면
 ├── "club" ─┐
 ├── "page" ─┼─  미연결 — 조용히 무시 (잘못된 곳으로 보내는 것보다 낫다)
 └── "url"  ─┘
```

| 결정 | 이유 |
|------|------|
| 본문을 배너 문서에 넣지 않는다 | 홈 진입마다 배너 N개를 읽는데, 안 여는 사용자까지 본문·사진 배열을 내려받게 된다. **탭했을 때만 doc 1건** |
| 화면은 하나, 내용만 갈아 끼운다 | 광고가 늘어도 앱 코드는 그대로. 인덱스 불필요(단건 get), 집계 없어 트리거도 불필요 |
| 광고 전용 페이지를 없애고 공지로 합쳤다 | 목적지가 배너 전용 페이지와 공지사항 둘로 갈려 **같은 광고를 두 벌 관리**해야 했다. 지운 것 — `promotions` 컬렉션 · `PromotionDetailScreen` · `notices.promotionId` · `BannerLinkType.promotion` · `seed_promotions.js` · promotions Rules |
| 배너에서 열 때만 문서를 조회 | 목록에서 탭한 경로는 이미 받은 모델을 그대로 넘긴다(**조회 0회**) |
| 전체화면이라 `pushHidingNavBar` | 광고 페이지를 열면 하단 nav 바를 내리고 돌아오면 복원 |

- 노출 기간(`startAt`·`endAt`)과 `order` 정렬은 `isActive==true` 쿼리 후 **클라에서** — 배너 건수가 적어 복합 인덱스를 유지할 이유가 없다
- 운영 배너 5건은 전부 `linkType:'notice'`. 광고 공지는 `notice_ad_*` id에 배너 이미지를 첨부 사진으로 넣는다
- 배너 카드의 `onTap`은 이번에 신설한 것 — 그전엔 `linkType`·`linkValue` 필드가 있어도 **죽어 있었다**

### 9.12 홈 진입 팝업 광고

앱을 켜고 홈에 처음 닿을 때 한 번 뜨는 전면 팝업. **정사각 사진 1장이 내용의 전부**이고, 탭하면 연결해 둔 공지 상세로 간다.

```
AuthGate 통과 ─▶ MainScaffold(홈 탭) 첫 프레임
 ▼ popupAdProvider          # popupAds where isActive==true — 앱 실행당 1회, read 1
 │   기간 필터(startAt ≤ now < endAt) ─▶ isPrimary ↓ → order ↑ ─▶ 맨 앞 1건만
 │   LocalPrefs 'popup_ad_hide_until_{popupId}' 확인 ─▶ now < until 이면 안 띄움
 ▼ 240ms 뒤 표시            # 배리어 + 글래스 카드 + 정사각 사진
 ├── 사진 탭 ──▶ linkType=='notice' ─▶ openNoticeDetail(linkValue)
 │               linkType=='none'   ─▶ 아무 일 없음
 ├── 닫기 · 배리어 탭 ──▶ 이번 실행만 안 뜸 (저장 없음)
 └── '1주일동안 안보기' ──▶ LocalPrefs = now + 7일 ─▶ 220ms 뒤 닫힘
```

**노출 판정 5개 조건**

| 순서 | 조건 | 판정 위치 |
|------|------|-----------|
| ① | `isActive == true` | 서버 쿼리 (Rules도 같은 값을 본다) |
| ② | `startAt ≤ now < endAt` | 앱 메모리 |
| ③ | `isPrimary` 내림차순 → `order` 오름차순 맨 앞 1건 | 앱 메모리 |
| ④ | `now ≥ hideUntil` (1주일 숨김 만료) | 기기 SharedPreferences |
| ⑤ | 앱 실행당 1회 | 화면 상태 (홈 탭 재진입·복귀로는 다시 안 뜬다) |

| 결정 | 이유 |
|------|------|
| 컬렉션을 `banners`와 나눈다 | 규격(1:1 ↔ 1.71:1)·수명·노출 지점이 다르다. `banners`에 `placement`를 더하면 **홈 배너 쿼리가 팝업 문서까지 읽어 온다** |
| 한 번에 1건만 | 겹쳐 띄우면 홈에 닿기까지 닫기를 여러 번 눌러야 한다 |
| `isPrimary`가 `order`보다 먼저 | 운영자가 "이건 무조건 맨 앞" 하나만 켜면 되게 — `order`만 있으면 새 광고를 맨 앞에 두려고 **기존 문서 번호를 전부 다시 매겨야** 한다 |
| `isPrimary`를 여러 개 켜도 안 깨진다 | 둘 이상이면 그중 `order`가 낮은 1건. **Rules는 다른 문서를 볼 수 없어 "1순위는 하나뿐"을 서버에서 강제할 수 없다** → 정렬이 항상 답을 하나로 좁히게 짠다. 배타 처리는 어드민 화면의 몫 |
| 제목·본문 필드를 두지 않는다 | 디자인에 텍스트 자리가 없다. 필드만 만들면 **운영자는 채우는데 앱은 안 그리는 상태**가 생긴다 |
| 공지 연결은 **선택**(`linkType:'none'` 기본) | 요구가 "공지 선택(필수 아님)". 연결하지 않으면 탭해도 아무 일 없다 |
| 목적지는 `notice` 하나 | 배너와 같은 분기·같은 화면을 그대로 쓴다 |
| '1주일동안 안보기'는 **기기 로컬** | 서버에 두면 팝업을 볼 때마다 write가 생기고, **비로그인 사용자는 저장할 키(uid)가 없다** |
| 숨김 키를 **문서 id별로** 나눈다 | 키가 하나면 A 광고를 1주일 숨긴 사용자가 그사이 올라온 **B 광고를 못 본다** |
| 숨김 기간 7일은 **앱 상수** | 운영자가 만질 값이 아니다. 서버 필드면 기기마다 다른 기간이 섞여 "왜 나만 또 뜨냐"를 재현할 수 없다 |
| 기간·정렬은 클라 메모리 | 등호 1개(`isActive`)뿐이라 **복합 인덱스 0개** |
| 노출수·클릭수 집계 없음 | 집계 필드가 없으니 트리거도 불필요 |
| 게이트 체인 **아래**에 붙는다 | 점검·강제 업데이트 차단 화면 위에 광고가 뜨면 안 된다 |
| 조회 실패는 **fail-silent** | 광고가 안 뜨는 것은 최악이 아니다. 오류 토스트를 띄우면 사용자는 자기가 뭘 잘못한 줄 안다 |

⚠ 내려간 광고의 로컬 키는 남는다. 개수가 적어 두고 있지만 늘어나면 활성 목록에 없는 키를 정리하는 단계를 붙일 것.

**팝업 이미지 규격**

| 항목 | 값 |
|------|-----|
| 비율 | **1 : 1 정사각** — 배너(1.71:1)와 다르다. 배너 이미지를 그대로 올리면 좌우가 잘린다 |
| 권장 원본 | 1080 × 1080 px |
| 포맷·용량 | JPEG 또는 WebP, 300KB 이하 |
| 안전영역 | 글자·로고는 가장자리 **8% 안쪽**. 모서리 radius 19로 깎이고, 정사각이 아닌 원본은 cover로 가운데만 남는다 |
| 가리는 것 | 없음 — 하단 바(AD · 1주일동안 안보기 · 닫기)는 사진 **바깥**에 있다 |

### 9.13 공지사항 게시 제어

앱은 **읽기 전용**. 작성·수정은 어드민 페이지 전용.

**노출 조건 3가지** — `NoticeModel.isVisibleAt(now)` 단일 소스, 목록·단건 조회 양쪽에 적용

| 조건 | 의미 | 우선순위 |
|------|------|----------|
| `isActive == true` | 게시 상태. false = 게시중단 | **기간보다 우선** |
| `publishedAt <= now` | 예약 게시 — 미래면 그 시각까지 안 보임 | — |
| `endAt == null \|\| endAt > now` | 게시 종료 — 지나면 문서를 지우지 않고 목록에서만 사라짐 | 메모리 필터 |

| 결정 | 이유 |
|------|------|
| `endAt`은 **메모리에서** 필터 | 서로 다른 필드에 범위 조건을 하나 더 걸면 복합 인덱스가 추가로 필요한데 공지 건수가 적어 얻는 게 없다. 대신 **`limit`이 종료된 공지까지 세므로** 실제 노출 건수가 limit보다 적어질 수 있다 |
| `isPinned`는 서버 `orderBy`에 안 넣는다 | 받아온 뒤 메모리에서 위로 올린다 — 3필드 인덱스를 유지할 이유가 없고 정렬 규칙을 바꿔도 인덱스 재배포가 불필요 |
| 게시 기간을 **Rules에 넣지 않는다** | 클라 시계가 서버보다 조금이라도 앞서면 쿼리 범위가 `request.time`을 넘어 **목록 전체가 permission-denied**가 된다. Rules는 `isActive`만 막는다 |
| **읽음 상태를 저장하지 않는다** | `users/{uid}/noticeReads` 방식은 공지를 열 때마다 write — 베타 규모에 과하다. NEW 배지는 `publishedAt`이 **7일 이내**인지로만 판정 |
| 광고 글도 같은 공지 화면 | 홈 배너·팝업이 보내는 곳이 곧 이 화면 |

쿼리: `where isActive==true + where publishedAt <= now orderBy publishedAt desc limit 50`.
인덱스: `notices(isActive ASC, publishedAt DESC)` — `publishedAt <= now`는 정렬 키와 **같은 필드**라 기존 인덱스로 처리된다(추가 인덱스 불필요).

> Rules 결과 — 게시중단 공지는 문서 ID를 알아도 못 읽는다. **예약 공지는 ID를 알면 읽힐 수 있으나** 앱 경로의 `getNotice`가 같은 기준으로 null 처리한다.

### 9.14 검색 트렌드 집계

```
searchLogs (클라 create 전용, TTL 14일)
 │ keyword · userId · source · createdAt · expireAt
 ▼ aggregateSearchTrends (매시 정각 KST)
 │ RANKED_SOURCES(input · suggestion) 만 카운트
 │ 랭킹 기준 = 고유 userId 수
 ├─▶ searchTrends/current            # 앱은 이 문서 1개만 read
 └─▶ searchHashtags.popularityRank
```

| 결정 | 이유 |
|------|------|
| 칩 탭 유입(`trend`·`hashtag`)은 랭킹에서 제외 | 넣으면 **1위가 계속 1위가 되는 되먹임** |
| raw count가 아니라 **고유 유저 수** | 1인이 반복 검색해도 1표 — 스팸·자기증폭 방지 |
| 스냅샷에 `runKey`(KST yyyyMMddHH) | 같은 시각 재실행 skip. 안 막으면 증감이 **방금 쓴 결과와 비교돼 전부 `same`으로 뭉개진다** |
| `uniqueUsers == 0`(fallback 자리)엔 증감 미표시 | 유저가 없는데 순위가 오르내리는 것처럼 보이면 안 된다. `realCount == 0`이면 제목도 '실시간'을 뗀다 |
| 해시태그는 큐레이션 문서 필수 | '입장료 무료'·'서비스 음료'는 검색어가 아니라 **전용 화면**으로 가야 해서 로그 자동 추출로는 라우팅을 만들 수 없다 |
| 문서를 8개보다 많이 두고 상위 8개만 노출 | 그래야 검색량에 따라 순서가 실제로 바뀐다 |
| 비랭킹 소스는 **write 자체를 안 한다** (2026.09.15) | 집계가 안 세는 로그에 write를 낼 이유가 없다. `SearchSource.ranked`가 서버 `RANKED_SOURCES`와 같은지는 `test/search_source_test.dart`가 지킨다 |

**갱신 주기** (`scheduleDecision()` — `compute_trends.ts`)

| 구간 | 인기 검색어 | 인기 해시태그 |
|------|-------------|---------------|
| 야간 20:00~09:00 (9시 포함) | 매시 | 매시 |
| 주간 10:00~19:00 | 2시간 (10·12·14·16·18) | 4시간 (12·16) |

주간 간격이 자정 기준 앵커(`hour % N`)라 **해시태그 갱신 시각은 항상 검색어 갱신 시각의 부분집합** → 로그 스캔 1회로 둘 다 처리한다. 클럽 검색이 밤에 몰리므로 야간을 촘촘하게.
매시 깨어나되 갱신 대상이 아니면 **Firestore 접근 없이 즉시 종료**.

순수 로직은 `functions/src/search/compute_trends.ts`에 **Firestore 의존 없이** 분리 — 되먹임 필터 · 고유유저 집계 · 증감 · fallback · 갱신주기 판단 전부 여기.
`searchLogs`는 클라 읽기 불가(Admin SDK 전용) · create만 · `keyword` 2~30자 · 필드 화이트리스트. **비로그인 검색은 Rules상 로깅되지 않는다.**

### 9.15 위치 기반 지역 판정

GPS 코드는 `data/datasources/local/device_location_datasource.dart` **한 곳만**. presentation은 `userLocationProvider`(keepAlive)만 본다.

```
SplashGate 진입
 ├─▶ geolocator 로 GPS 1회 조회 (권한 팝업도 여기, 5초 타임아웃)
 │    서비스 꺼짐 · 권한 거부 · 타임아웃 → 예외 대신 null → 폴백 좌표(홍대)
 └─▶ userLocationProvider 갱신
      ├── 홈 위치 칩 라벨 · 홈 인사말
      ├── 홈 '주변 클럽' 섹션
      ├── 주변 탭 최초 조회 중심
      └── 카테고리 페이지 거리 표기
```

**좌표 → 지역 이름 (`AppGeo.areaOf()`) — 2단계**

| 단계 | 기준 | 반경 | 비고 |
|------|------|------|------|
| ① | 클럽 상권 `AppGeo.hotspotCenters` | 2km | **최근접 우선** — 홍대·신촌은 1.2km라 반경만으론 못 가린다 |
| ② | 전국 시군구 `korea_regions.dart` (252개) | 상한 60km | **표시 전용 라벨**. `clubs.area`와 무관 |

상권이 시군구보다 먼저라 홍대에 있으면 '마포구'가 아니라 **'홍대'**로 뜬다.

**국내 밖(60km 밖) 처리** — 해외 좌표를 그대로 두면 반경 3~30km 안에 클럽이 0곳이라 홈 '주변 클럽'·주변 탭이 빈 화면이 된다. `AppGeo.overseasFallbackAreas`(홍대·건대·이태원·강남) 중 **앱 실행마다 랜덤 1곳**의 좌표를 빌리고, 라벨만 `AppGeo.outsideKoreaLabel`(**'위치 확인 불가'**)로 바꾼다.

- 좌표를 빌린 걸 숨기고 '강남'이라 쓰면 **거짓 정보**라 라벨은 분리. 화면 문구는 **`areaLabel`로만** 읽을 것(`area`엔 대체한 상권명이 들어간다)
- 뽑은 상권은 앱 실행 내내 고정 — 칩을 누를 때마다 주변 클럽이 갈아엎히면 안 된다

**상권명은 `clubs.area` 값과 정확히 같아야 한다** — 지역 필터와 거리표가 같은 문자열을 쓴다. DB에 상권을 추가하면 `AppGeo.hotspotCenters`에도 반드시 추가.

**구가 있는 시는 시가 아니라 구를 넣는다** — 일반구를 둔 12개 시(수원·성남·안양·안산·고양·용인·부천·청주·천안·전주·포항·창원)는 시 항목을 빼고 **구 35개**로 대체. 시 하나로 두면 분당·일산·수지가 전부 '성남시'·'고양시'로 뭉개진다. 화성시는 일반구 미설치라 아직 시 단위.
이름이 겹치는 중구·동구·남구·서구·북구·강서구·고성군·포항 남북구는 '서울 중구'처럼 시도를 앞에 붙였다(경기 광주시도 광주광역시와 구분). **라벨 유일성은 테스트가 지킨다.**

- `UserLocation`은 `==`를 구현한다 — 같은 좌표로 다시 set해도 watcher가 안 깨어난다. `setLocation`은 **50m 미만 이동도 무시**(GPS 지터로 목록이 재계산되지 않게). 홈 섹션·주변 뷰모델은 `select((l) => (lat, lng))`로 좌표만 본다
- ⚠ **`AppGeo.useFixedLocation`은 false가 정상** — true면 GPS를 아예 안 읽고 전 화면이 홍대로 고정된다(권한 팝업도 안 뜸). 화면 확인용 스위치이므로 **true인 채로 커밋하지 말 것**
- 위치 권한 문구는 설정돼 있음 — Android `ACCESS_FINE/COARSE_LOCATION`, iOS `NSLocationWhenInUseUsageDescription`

### 9.16 고객센터 문의 · 답변

```
앱 (presentation/support/)                        운영자
 SupportScreen        목록(스트림)                 Firebase 콘솔에서 문서 직접 편집
 InquiryWriteScreen   작성 → Storage → 문서 생성     answer · status='answered'
 InquiryDetailScreen  상세 + 답변 + readAt 1회 쓰기   answeredAt · answeredBy
```

| 결정 | 이유 |
|------|------|
| **답변 필드는 앱이 못 고친다** | Rules가 사용자 update를 `readAt` 한 키로 제한. 안 막으면 스스로 '답변완료'로 바꾸거나 **답변 문구를 지어낼 수 있다** |
| create에서 값까지 검사 | `status=='pending'`·`answer==''`·`answeredAt==null` 고정 + 필드 화이트리스트(`keys().hasOnly`) — `searchLogs`와 같은 방식 |
| 읽음 상태(`readAt`)는 **서버에 둔다** | 공지는 열 때마다 write가 생겨 안 뒀지만, 문의는 사용자당 문서가 몇 건이고 '안 본 답변' 배지가 **기능의 핵심**이라 기기 간에 맞아야 한다. 쓰기는 답변 도착 후 상세를 처음 열 때 **1회** |
| 목록을 **스트림**으로 | 푸시가 없어 답변 도착을 알릴 다른 경로가 없다. 화면을 열어 두면 그 자리에서 '답변완료'로 바뀐다 |
| 알림은 앱 안 배지뿐 | FCM 인프라가 전혀 없다. 마이페이지 행의 안 본 답변 수는 **목록 스트림에서 메모리 집계**라 추가 쿼리 0 |
| Storage read를 **공개하지 않는다** | 문의 사진은 개인 자료. 다른 경로(`clubs/**`·`reviews/**`)와 다른 유일한 규칙 |
| 문의 삭제는 어드민만 | 사용자가 지우면 답변 이력이 사라져 **분쟁 때 근거가 없다** |
| 스팸 제한은 앱에서만 | Rules로는 건수를 셀 수 없다. 서버 제한이 필요해지면 onCall 함수로 옮긴다 |
| Cloud Functions 추가 없음 | 집계 필드가 없고 답변은 운영자가 직접 쓴다 |

업로드 순서 — **`inquiryId` 선발급 → Storage 업로드 → 문서 생성**(리뷰 작성과 같다). 업로드가 실패하면 문서가 안 생겨 '안 보내졌다'가 정확하게 전달된다.

> ⚠ `inquiries` Storage 경로의 **첫 칸이 `uid`**다 — Rules가 이 자리로 소유자를 판정한다. 리뷰는 `clubId` 자리라 자리 순서를 헷갈리지 말 것.
> ⚠ 비공개 read는 **경로를 훑어 캐가는 것만** 막는다 — 문서에 저장하는 `getDownloadURL()`은 토큰이 박힌 URL이라 그 URL을 아는 쪽은 규칙과 무관하게 받아간다(리뷰와 같다).

**배포 현황 (2026.09.06)** — Rules·인덱스·Storage 배포 완료, 인덱스 2개 READY. **실계정 종단 검증 11건 전부 통과**: 비인증 목록 403 / 사용자 생성 200 / 제목 1자 위반 403 / 사용자의 `status`·`answer` 수정 403 / `readAt` 수정 200 / 사용자 삭제 403 / 어드민 무필터 목록 200 / 어드민 답변 등록·조회·삭제 200.

> Auth에 남아 있는 `vybe.test.admin@example.com` 등 3개 계정은 클레임이 `{"role":"admin"}` 같은 **옛 스키마**라 지금 Rules(`token.admin == true`)로는 아무 권한도 없다. 필요해지면 Admin SDK로 `{ admin: true }`를 다시 심어야 한다.

 ├── 📁 photos/{photoId}           # 사진탭 (카테고리별)
 └── 📁 reviews/{reviewId}         # 인앱 리뷰

📁 favorites/{favoriteId}          # 찜 (top-level)
📁 banners/{bannerId}              # 홈 배너
📁 popupAds/{popupId}              # 홈 진입 팝업 광고

📁 notices/{noticeId}              # 공지사항
📁 searchLogs/{logId}              # 검색 로그 원본 (클라 create만, TTL 14일)

### 10.1 `users/{uid}`

| 필드 | 타입 | 설명 |
|------|------|------|
| `uid` | string | Firebase Auth UID (PK) |
| `name` | string | **의미 고정 — 본인인증으로 받은 실명.** 남에게 보이는 자리에는 절대 쓰지 않는다. 표시 이름은 `nickname`. 본인에게만 '내 정보 수정 > 가입 정보' 카드에서 **마스킹**된 형태로 보인다 |
| `phone` | string | 본인인증 완료된 전화번호 (중복 가입 방지 기준) |
| `birthDate` | string | 생년월일 `YYYYMMDD` |
| `gender` | string | `"male"` \| `"female"` — 주민번호 뒷자리 첫 숫자에서 도출(홀수 남/짝수 여). 영문 키만 저장. **알 수 없으면 필드를 아예 쓰지 않는다**(빈 값 = '미입력'과 구분 불가). 도출은 `genderFromCode()` 한 곳 |
| `nickname` | string | **서버 전용.** 앱 전체의 표시 이름. 2~12자 · 한글/영문/숫자 · 중복 불가(`nicknames/{key}` 예약이 강제). 쓰기는 `updateUserProfile` 하나뿐 — Rules가 클라 쓰기를 막고 **create에도 이 키를 실을 수 없다**. 빈 값/필드 없음 = 아직 배정 안 된 계정 → 화면은 중립 라벨 **`VYBER`**. **폴백을 `name`으로 두면 안 된다** |
| `profileImageUrl` | string | **서버 전용.** `users/{uid}/profile_{millis}.jpg`. 빈 값 = 기본 아바타(실루엣). `nickname`과 한 트랜잭션에 저장돼야 해서 같이 잠갔다 — 나눠 쓰면 반쪽만 저장되는 상태가 생긴다. **파일명에 타임스탬프**를 붙여 매번 다른 경로에 올린다(덮어쓰면 캐시·CDN이 옛 사진을 계속 보여준다) |
| `provider` | string | `"kakao"` \| `"naver"` \| `"identity"` \| `"apple"` — 앱 `saveUserProfile`이 쓰는 4값. 트리거 `onUserCreated`는 uid prefix에서 도출 |
| `isVerified` | boolean | 본인인증 완료 여부(초기값 false). **세션 유효성의 단일 기준으로 승격** — false로 되돌리면 다음 실행에서 자동 로그아웃. 값을 true로 올리는 곳은 `verifyIdentity`·`setUserProfile` 둘뿐 |
| `agreements` | map | 약관 동의 기록 — `{ <key>: { agreed, version, agreedAt } }`. 키는 `terms`·`privacy`·`location`·`marketing`(= `LegalDoc.name`) + `age19`. **비동의도 false로** · `version`은 문서 개정일 `YYYY-MM-DD` · `agreedAt`은 **중첩 map 안의 serverTimestamp**(list로 바꾸면 쓰기 실패). 가입 때 한 번만 쓴다. **`marketing`만 예외로 가입 후에도 바뀐다**(설정 토글 — 점 표기로 그 항목만 교체) |
| `status` | string | `"active"` \| `"pendingDeletion"` — 필드가 없으면 active로 간주. **서버 전용** |
| `deletedAt` | timestamp? | 탈퇴 요청 시각. **서버 전용** |
| `purgeAt` | timestamp? | `deletedAt + 30일` = 완전 파기 예정 = 재가입 가능 시점. **서버 전용** |
| `deletionReason` | string? | 탈퇴 사유(선택 설문). 안 고르면 빈 문자열 |
| `createdAt` | timestamp | 가입 시각. **문서를 처음 만들 때만** 쓴다(Rules가 이후 변경을 막는다) |
| `updatedAt` | timestamp | 수정 시각. **로그인만으로는 갱신 안 됨**(재로그인 경로는 users 쓰기 0) |

> ⚠ **`createdAt`은 앱이 쓴다 — `onUserCreated` 트리거에 맡기지 않는다 (2026.08.18)**
> 원래 설계는 Auth 신규 유저 트리거가 채우는 것이었는데 **그 트리거가 실행되지 않고 있다**. `phoneLogin`이 새 uid를 만든 시각에 `onUserCreated` 호출 로그가 **0건**이고, 그렇게 만들어진 `phone:` 문서엔 전부 `createdAt`이 비어 있다(2026-04에 만들어진 `kakao:` 문서엔 있다 — 그 사이에 죽었다).
> 이제 `setUserProfile`이 **문서가 없을 때만** `createdAt`을 같이 쓴다. Rules의 update 규칙이 `createdAt` 변경을 막으므로 **이미 비어 있는 문서는 앱에서 못 메운다** — 서버 스크립트 백필 필요.

### 10.2 `nicknames/{key}`

| 필드 | 타입 | 설명 |
|------|------|------|
| (문서 ID) | string | `key` = 닉네임을 **소문자로 접은 값**. **문서의 존재 자체가 예약** — 같은 ID로 두 번 만들 수 없다는 성질이 곧 유일성(Firestore엔 unique 제약이 없다) |
| `uid` | string | 이 닉네임을 쓰는 유저. **필드는 이것 하나뿐** |

- 소문자로 접는 이유 — `VYBE`와 `vybe`를 다른 닉네임으로 두면 **사칭이 쉽다**. 한글은 대소문자가 없어 영향 없고, 화면에 보이는 값은 `users.nickname`(원본 대소문자)
- **클라는 read도 못 한다**(`allow read, write: if false`) — 존재 여부를 물어볼 수 있으면 닉네임을 열거할 수 있다. 중복 판정은 함수가 트랜잭션 안에서
- 조회용이 아니라 충돌 검출용이라 **인덱스 불필요**(문서 ID로만 접근)
- 예약 회수는 **파기(`purgeDeletedUsers`) 때만** — 탈퇴 요청 시점에 풀면 보관 기간 안에 복구한 계정이 그사이 남이 가져간 닉네임을 되찾을 수 없다

### 10.11 `banners/{bannerId}`

| 필드 | 타입 | 설명 |
|------|------|------|
| `bannerId` | string | PK (= doc.id fallback) |
| `imageUrl` | string | 권장 원본 **1026 × 600 px** (비율 1.71:1) |
| `linkType` | string | `"notice"` \| `"club"` \| `"page"` \| `"url"`. `BannerLinkType` enum — **알 수 없는 값은 none**(이동 없음) |
| `linkValue` | string | `notice`: noticeId / `club`: clubId / `page`: 화면 키 / `url`: URL |
| `order` | number | 정렬 순서(오름차순) |
| `isActive` | boolean | 노출 여부 |
| `startAt` / `endAt` | timestamp | 노출 시작 · 종료 |

| 항목 | 값 |
|------|-----|
| 권장 원본 | **1026 × 600** (3x). 더 선명히 하려면 1368 × 800 (4x, 같은 비율) |
| 포맷·용량 | JPEG 또는 WebP, **300KB 이하** |
| 상하 안전영역 | 위·아래 각 **9%**(1026×600 기준 54px)가 잘릴 수 있다 — 글자·로고는 그 안쪽 |
| 우하단 회피 | `1 / 4` 카운터 pill이 덮는다 — 오른쪽 아래 약 **110 × 40px** 비울 것 |
| 하단 45% | 앱이 검정 그라데이션(`0xC708080C`)을 덮는다 → **밝은 글자** |

> ⚠ **기기마다 카드 비율이 달라진다** — `.w`(가로 비)와 `.h`(세로 비)가 따로 스케일돼 폭·높이가 다른 계수로 늘어난다. iPhone SE(375×667)에서 **2.08:1**로 가장 납작하고 iPhone 15는 1.71:1. `cover`라 납작한 기기에서 위아래가 잘리므로 **안전영역 9%는 SE 기준**이다.
> ⚠ 이 비율은 **홈 배너 전용**. 같은 이미지를 광고 공지(`notice_ad_*`) 첨부로도 쓰는데, 공지 본문 첨부는 `BoxFit.fitWidth` 자리라 잘리지 않는다.

### 10.19 `appConfig/{platform}` (문서 2개 고정: android · ios)

| 필드 | 타입 | 설명 |
|------|------|------|
| `platform` | string | PK `"android"` \| `"ios"` (= doc.id) |
| `minVersion` | string | 이 버전 미만이면 **강제 업데이트**(전체화면 차단). 비면 강제 없음 |
| `latestVersion` | string | 이 버전 미만이면 **업데이트 권유**(닫을 수 있는 바텀시트). 비면 권유 없음 |
| `storeUrl` | string | 스토어 링크 — 앱 배포 없이 바꿀 수 있게 서버에. 비면 **Android만** `market://details?id={packageName}` 폴백 |
| `updateTitle` / `updateMessage` | string | 업데이트 안내 제목·본문. 비면 화면 기본 문구 |
| `isMaintenance` | boolean | **점검 모드** — 버전과 무관하게 진입 차단. 버전 판정보다 **우선**(최신 버전 유저도 막힌다) |
| `maintenanceMessage` | string | 점검 안내 문구. 비면 기본 문구 |
| `updatedAt` | timestamp | 수정 시각 |

**판정 4단계** (`decideVersionAction()` — `core/utils/version_utils.dart`)

| 순위 | 조건 | 화면 | 닫기 |
|------|------|------|------|
| 1 | `isMaintenance == true` | 점검 안내 전체화면 | **불가** (`PopScope canPop:false`) |
| 2 | 현재 버전 < `minVersion` | 강제 업데이트 전체화면 | **불가** |
| 3 | 현재 버전 < `latestVersion` | 권유 바텀시트 | 가능 · 앱 실행당 1회 |
| 4 | 그 외 · 조회 실패 · 타임아웃 · 버전 미상 | 통과 | — |

- 버전 비교는 문자열이 아니라 **파트 단위 숫자 비교** — 그래야 `1.10.0 > 1.9.0`이 맞게 나온다
- 빌드번호(`+7`)·프리릴리스(`-beta1`)는 **무시** → **핫픽스도 patch를 올려야** 게이트가 구분한다
- 예외를 삼키는 곳은 `VersionCheck` 뷰모델 **한 곳뿐** — datasource는 그대로 던진다(여러 층에서 삼키면 어디서 실패했는지 추적 불가)
- ⚠ **Rules에서 read에 auth 조건을 걸지 않는다** — 게이트는 **로그인 전에** 읽는다. auth를 요구하면 비로그인 유저가 안내를 영영 못 받는다
- ⚠ **Android/iOS 문서를 나눈 이유** — 스토어 심사·배포 시점이 달라 한쪽만 `minVersion`을 올릴 수 있어야 한다

#### 운영 주의사항 — 값 하나로 전 유저를 막을 수 있다

| 상황 | 해야 할 것 / 하면 안 되는 것 |
|------|------------------------------|
| 강제 업데이트 켜기 | **새 빌드가 스토어에 실제 게시된 것을 확인한 뒤** `minVersion`을 올린다. **심사 중에 미리 올리면 심사자 기기가 차단 화면에 막혀 리젝**된다. Android 단계적 출시(%) 중이면 **100% 도달 후** |
| 잘못 올렸을 때 | `minVersion`을 빈 문자열로 되돌리면 **즉시 해제** — 앱 재배포 불필요. 기기 반영은 다음 실행 또는 복귀 시점 |
| 반영 시점 | 앱 **실행 시** + **복귀(resumed) 시**에만 조회. 켜 둔 채 화면만 옮기는 동안엔 반영 안 됨(의도된 동작) |
| 점검 모드 | `isMaintenance=true`는 **최신 버전 유저까지 전원 차단**. 끄면 '다시 시도'로 즉시 복귀 |
| 버전 값 형식 | `"1.2.0"` 숫자·점만. `pubspec.yaml`의 `version:`과 스토어 버전명이 **일치**해야 판정이 맞는다 |
| **문서 삭제 금지** | 문서가 없으면 게이트가 항상 통과(fail-open) = 사실상 꺼짐. 끄고 싶으면 **문서를 지우지 말고 필드를 비운다** |
| `storeUrl` | 비면 **Android만** 폴백. **iOS는 폴백 없음** — App Store 등록 후 `https://apps.apple.com/kr/app/id{앱ID}` 필수. 안 채우면 업데이트 버튼이 토스트만 띄운다 |
| 오프라인 유저 | `get()`이 캐시본을 주거나 3초 타임아웃 → **둘 다 통과**. 오프라인에선 강제 업데이트가 걸리지 않는다(의도된 fail-open) |
| 쓰기 권한 | Custom Claim `admin: true`만. 어드민 페이지 전까진 `scripts/seed_app_config.js` 또는 콘솔 |

### 11.2 자동 트리거 (6개)

| 함수 | 트리거 | 역할 |
|------|--------|------|
| `onUserCreated` | Firebase Auth 신규 유저 생성 | `users/{uid}` 문서 자동 생성(`provider`·`createdAt`). 이미 존재하면 덮어쓰지 않음. **⚠ 현재 실행 안 됨** — Custom Token 로그인으로 Auth 유저가 생겨도 호출 로그가 없다. `createdAt`은 앱(`setUserProfile`)이 쓰도록 옮겨 지금은 이 함수 없이도 동작한다. **원인 조사 필요** |
| `onFavoriteCreated` | `favorites/{id}` 생성 | `clubs.favoriteCount += 1` (`FieldValue.increment`) |
| `onFavoriteDeleted` | `favorites/{id}` 삭제 | `favoriteCount -= 1` (0 미만 방지). **`isHidden==true`면 skip** |
| `onReviewCreated` | `reviews/{id}` 생성 | `ratingSum += rating`, `reviewCount += 1`, `rating = ratingSum/reviewCount` |
| `onReviewDeleted` | `reviews/{id}` 삭제 | 감산 후 `count>0` 재계산 / 0이면 `rating=0`. **`isHidden==true`면 skip** |
| `onReviewUpdated` | `reviews/{id}` 수정 | `ratingSum += (new - old)`, `rating` 재계산. **`isHidden` 전이거나 이미 숨겨진 리뷰면 skip** |

> ⚠ **`isHidden` 가드가 왜 필요한가** — 탈퇴 시 집계 감산은 `requestAccountDeletion`이 **직접** 한다. `isHidden=true` 세팅은 문서 update라 `onReviewUpdated`가 발화하고, 30일 뒤 파기 때는 `onReviewDeleted`·`onFavoriteDeleted`가 발화한다. 가드가 없으면 같은 리뷰가 **두 번 깎여** `rating`·`favoriteCount`가 **음수**가 된다.

### 11.3 스케줄 (3개) — Cloud Scheduler + Pub/Sub (Blaze 필요)

| 함수 | 스케줄 | 역할 |
|------|--------|------|
| `cleanupPastPerformances` | 매일 KST 04:00 | 종료된 공연 삭제. `startAt < now - 8h`(`PERFORMANCE_DURATION_HOURS`)만 → 예정·진행 중(새벽) 공연 보존. 500개씩 배치 |

| `purgeDeletedUsers` | 매일 KST 04:30 | 보관 30일 지난 탈퇴 계정 완전 파기 — Firestore 문서(리뷰·사진·찜·검색기록·users) + **`nicknames/{key}` 예약 회수** + Storage 파일(`reviews/`·`users/`) + Auth 유저. 회차당 50명, 한 명 실패해도 다음으로 진행 |

### 11.4 구현 시 주의사항

- **자동 집계 필드 직접 수정 금지** — `favoriteCount` · `ratingSum` · `reviewCount` · `rating`은 반드시 Cloud Functions으로만
- `ratingSum` / `reviewCount` 증감은 **`FieldValue.increment()`** (동시 요청 정합성)
- `rating`은 **트랜잭션**으로 `ratingSum / reviewCount` 계산 후 저장
- `onReviewDeleted`에서 `reviewCount`가 0이 되면 `rating = 0` 처리
- 소셜 UID 형식: `naver:{naverId}` · `kakao:{kakaoId}` · `phone:{phone}`
- `onUserCreated`는 문서가 이미 존재하면 **덮어쓰지 말 것**(중복 실행 방어)
- `cleanupPastPerformances`는 `date`(YYYYMMDD)가 아닌 **`startAt`(Timestamp) 기준** 삭제 — 새벽 공연 오삭제 방지
- `nickname`·`profileImageUrl`은 **`updateUserProfile`만** 쓴다 (Rules가 클라 쓰기를 막는다)
- `purgeDeletedUsers`는 **users 문서를 지우기 전에** `nickname`을 읽어 둬야 한다 — 순서를 뒤집으면 예약 key를 알 방법이 없어 그 닉네임이 **영원히 잠긴다**

### 12.1 Firestore

**`users` update 규칙 (실제 형태)**

```js
match /users/{uid} {
  allow read: if request.auth != null && request.auth.uid == uid;

  // 가입 — 닉네임은 함수가 나중에 쓴다. 클라가 실어 보내면 거부.
  allow create: if request.auth != null
                && request.auth.uid == uid
                && !request.resource.data.keys().hasAny(['nickname']);

  allow update: if request.auth != null
                && request.auth.uid == uid
                && !request.resource.data.diff(resource.data).affectedKeys()
                     .hasAny(['uid', 'provider', 'createdAt',
                              'status', 'deletedAt', 'purgeAt',
                              'nickname', 'profileImageUrl']);
}

// 예약(유일성) 전용 — 규칙을 안 적어도 기본 거부지만 일부러 적어 둔다:
// '빠뜨린 것'과 '막은 것'을 다음 사람이 구분할 수 있어야 한다.
match /nicknames/{key} {
  allow read, write: if false;
}
```

> ⚠ **숨김 판정은 `resource.data.get('isHidden', false) == false`** — `resource.data.isHidden != true`로 쓰면 안 된다. Rules에서 **없는 필드에 직접 접근하면 평가가 에러로 떨어져 거부**되므로 백필 전 문서가 통째로 막힌다.
> ⚠ **커스텀 클레임도 `token.get('clubIds', [])`로 읽는다** — 같은 함정.
> ⚠ **`is int`가 아니라 `is number`** — 클라 SDK가 숫자를 double로 실어 보내면 `is int`는 업주의 모든 저장을 거부한다.

| 경로 | 읽기 | 쓰기 |
|------|------|------|
| `clubs/**` | 누구나 | 어드민만, 10MB 이하, 이미지만 |
| `reviews/**` | 누구나 | 로그인 유저, 10MB 이하, 이미지만 |

> ⚠ **`allow write`에 delete를 같이 두지 말 것** (2026.09.15 수정·배포) — 삭제 요청엔 `request.resource`가 **null**이라 `request.resource.size`·`contentType`을 보는 순간 평가가 에러로 떨어져 **본인 파일도 못 지운다**(`[firebase_storage/unauthorized]`). 프로필 사진을 바꿀 때마다 옛 파일이 고아로 남던 원인 — 삭제 실패는 앱이 삼켜서(`deleteFileByUrl`) 화면은 멀쩡하고 로그에만 보인다.
> → 전 경로를 **`allow create, update`(용량·타입 검사) + `allow delete`(주체만 검사)**로 쪼갰다.

> ⚠ `inquiries`의 비공개 read는 **경로를 훑어 캐가는 것만** 막는다 — 문서에 저장하는 `getDownloadURL()`은 토큰이 박힌 URL이라 그 URL을 아는 쪽은 규칙과 무관하게 받아간다(리뷰와 같다).

## 15. 환경변수 · 배포

### 15.1 환경변수 (dotenv)

API 키는 `.env`로 관리하며 **절대 git에 커밋하지 않는다**. `.env.example`·`functions/.env.example`은 키 이름만 담아 커밋.

**Flutter — 프로젝트 루트 `.env`**

```
KAKAO_NATIVE_APP_KEY=...     # main.dart: KakaoSdk.init
NAVER_MAP_CLIENT_ID=...      # main.dart: FlutterNaverMap().init
ALGOLIA_APP_ID=...           # algolia_club_search_datasource
ALGOLIA_SEARCH_API_KEY=...   # 반드시 Search-Only 키 (Admin/Write 키 금지)
```

`main.dart` 초기화 순서: `dotenv.load` → `Firebase.initializeApp` → `KakaoSdk.init` → 네이버 지도.

> ⚠ 네이버 **로그인** clientId/clientSecret은 dotenv가 아니라 **네이티브 설정**에 있다 — `android/app/src/main/AndroidManifest.xml`의 `com.naver.sdk.*` 메타데이터와 `ios/Runner/Info.plist`. 서버는 클라가 넘긴 accessToken만 검증하므로 이 값들이 필요 없다.

**Cloud Functions — `functions/.env`** (서버가 실제로 읽는 키는 **이 둘뿐**)

```
PORTONE_IMP_KEY=...          # verifyIdentity — 포트원 토큰 발급
PORTONE_IMP_SECRET=...       # verifyIdentity — 포트원 토큰 발급
```

> ⚠ **현재 배포본에 이 키가 안 실려 있다 (2026.08.20 확인)** — `verifyIdentity`의 런타임 환경변수에 `PORTONE_*`가 없어 호출하면 `internal`("포트원 API 키가 설정되지 않았습니다")로 실패한다. 앱이 아직 이 함수를 부르지 않아 드러나지 않았을 뿐(문자 인증이 `'123456'` 하드코딩).
> `firebase deploy`는 `functions/.env`를 읽어 **런타임 환경변수로 올린다** — **파일이 없으면 조용히 없는 채로 배포된다(경고 없음)**. 로그인 3종은 서버 시크릿을 안 써서 영향 없다.

### 15.3 배포 순서가 중요한 작업

| 작업 | 순서 | 어기면 |
|------|------|--------|
| **프로필 수정** | ① `functions:updateUserProfile,purgeDeletedUsers` → ② 앱 → ③ `firestore:rules` | 함수 없이 앱을 내보내면 가입 마지막 닉네임 배정·프로필 저장이 전부 실패(가입 자체는 안 막힌다 — 배정 실패를 삼키고 `VYBER`로 진행). Rules를 먼저 올려도 구버전 앱엔 저장 경로가 없어 실질 위험 없음 |
| **회원 탈퇴** | ① 백필 → ② 인덱스 → ③ Rules·Functions → ④ 앱 | 앱을 먼저 내보내면 `where isHidden == false`가 필드 없는 문서를 못 잡아 **리뷰 탭·사진 탭이 빈 화면**. 인덱스가 없으면 `failed-precondition`. **지금은 서버가 다 돼 있어 앱은 아무 때나** |
| **탈퇴 복구** | 자유 (양방향 안전) | 서버만 먼저 → 구앱은 필드를 무시하고 복구된 계정으로 그냥 로그인(안내 토스트만 없음). 앱만 먼저 → 구서버가 `restored`·`restorable`을 안 줘 false 폴백 → 예전처럼 차단될 뿐 |
| **시간대별 무료입장** | ① seed 백필 → ② Algolia Indexable Fields + 재색인 → ③ 앱 `_requiredFields` → ④ 앱 배포 | ① 백필 전 앱 배포 = 무료 페이지 빈 화면 ② 재색인 전 `_requiredFields` 확대 = 전 hit `complete=false` → **read가 검색당 10건씩 되살아난다** |
| **전화번호 주인 판정** | 자유 | 구앱은 `method`를 안 보내지만 서버가 `'identity'` 기본값을 잡고, 구앱은 `isDuplicate`만 읽으므로 기존과 같이 동작(차단). 신앱 + 구함수도 `sameAccount ?? false` → 차단. **어느 쪽이든 지금보다 나빠지지 않는다** |

| **알림 화면** | UI 완성 · 더미 데이터 + 1.1초 가짜 로딩(`_kFakeLoadDelay`) → repository 호출로 교체 |
| **테이블 데이터** | 실제 배치·가격 조사 (현재 seed 샘플 3곳) |
| **업주 웹** | `partner/` 3파일 배포 + 업주 계정 생성 + 클레임 부여 |
| **법적 고지** | 개인정보처리방침에 '30일 보관' 명시(법무 확인) · `legal/` 첫 배포 여부 결정 |
| **createdAt 백필** | `phone:` 유저 문서의 빈 `createdAt` — Rules가 앱 쓰기를 막아 **서버 스크립트 필요** |

### 17.3 미구현 ⬜

| 항목 | 비고 |
|------|------|
| **문자 인증 실연동** | 코드 `'123456'` 하드코딩 · `phoneLogin`이 번호만 받으면 토큰 발급. **출시 차단 항목** |
| Apple 로그인 | 버튼 존재, `onTap` 빈 함수 |
| 푸시 알림(FCM) | `firebase_messaging` 미설치 · APNs 설정 없음 |
| **어드민 페이지** | 공지 작성 · 배너 · 팝업(1순위 배타 처리 포함) · 클럽 편집 · 버전 정책 · 문의 답변 · 편의시설 · 무료입장 창 편집 · `pendingDeletion` 조회/즉시 파기 — **전부** |
| 패스·지갑 탭 | 화면 없음(플레이스홀더도 삭제됨) |
| 세부 장르 필터 | `clubs.genreStyles` 폐기 — 실 조사 데이터 + 어드민 UI 선행 |
| 약관 개정 재동의 화면 | `version`은 쌓아만 두고 있다 |
| 탈퇴 철회 UI | 범위 밖 — 로그인이 곧 복구. 필요해지면 `cancelAccountDeletion`으로 역연산 |
| 웨이팅·예약·결제·분실물 | 베타 범위 밖 (테이블은 **표시 전용**, 예약은 매장 전화 안내) |

### 17.4 검증 못 한 것

| 항목 | 이유 |
|------|------|
| 탈퇴 실계정 종단 테스트 | 커스텀 토큰 발급에 필요한 `iam.serviceAccounts.signJwt`(Service Account Token Creator) 권한이 없다. 앱 배포 후 실기기에서 확인 |
| `onUserCreated` 미실행 원인 | 호출 로그가 0건인 것만 확인. 원인 미조사 |

## 18. 로드맵

```
1. 주변 ↔ 상세 페이지 연동 마무리 (진행 중)
        ↓
2. 프로필 수정 배포 (함수 → 앱 → Rules) + 알림 화면 실연동
        ↓
3. 패스·지갑 탭 구현 (탭 슬롯 재배치 포함)
        ↓
4. Rules·인덱스 배포 검증 + 본인인증(verifyIdentity) 실연동
   ⚠ 선행: functions/.env 에 PORTONE_IMP_KEY·PORTONE_IMP_SECRET 채우고 재배포
        ↓
5. 문자 인증 실연동 (Firebase Phone Auth) — 출시 차단 항목
        ↓
6. Apple 로그인
```
